# Ground banner matches in vendor bounds

As of 12 November 2026, Chaca should keep two vulnerability databases and refuse a third shortcut. Lockfile ecosystems belong in OpenSSF OSV per-ecosystem zips, which already ingest the GitHub Advisory Database; nginx, OpenSSL, Apache httpd, the PHP interpreter, and WordPress core are absent from that ecosystem list and from GitHub’s reviewed registries, so their upgrade strings have to be snapshotted from the vendor pages, with an NVD CPE interval used only when NIST has actually enriched that product. A `Server`, `X-Powered-By`, or generator token is not a package coordinate: Grype, Trivy, osv-scanner, and Dependency-Check never document a match from those headers, and applying an upstream range to a distro build is the backport false positive those tools exist to avoid. Version comparison has to follow the record’s own range type, print an advisory id plus that source’s upgrade or an explicit “no fix,” and must not treat end of life as a CVE. The passive work still worth adding before more scan code is header-decidable, led by the ASVS 5.0.0 Level 1 cookie-name prefix that neither ZAP’s release rules nor MDN HTTP Observatory score. Request behavior should keep the existing split between an in-flight cap and a shared send-rate, set a timeout because reqwest 0.12.28 documents none, and should not copy Nuclei’s 150 requests per second as a target-safety setting.

## Lockfile zips and vendor pages are different databases

Chaca’s fingerprints and any future lockfile scan do not share a feed. On 12 November 2026, OSV’s `ecosystems.txt` listed 48 lines and included `npm`, `Go`, `crates.io`, `Packagist`, `Maven`, `PyPI`, `GIT`, `Debian`, `Ubuntu`, and `Alpine`. It did not include an ecosystem whose name contained nginx, OpenSSL, Apache httpd, PHP, or WordPress ([ecosystems.txt](https://storage.googleapis.com/osv-vulnerabilities/ecosystems.txt)). GitHub reviews advisories only for a registry list that stops at the same place: Composer, Hex, Go, GitHub Actions, Maven, npm, NuGet, PyPI, Pub, RubyGems, crates.io, and Swift. Unreviewed rows are automatic NVD imports that GitHub does not validity-check, and Dependabot does not alert on them ([About the GitHub Advisory Database](https://docs.github.com/en/code-security/security-advisories/working-with-global-security-advisories-from-the-github-advisory-database/about-the-github-advisory-database)). Packagist therefore covers PHP libraries in a Composer lockfile, not the interpreter version an `X-Powered-By` banner shows ([OSV data sources](https://google.github.io/osv.dev/data/)).

The offline artifact for lockfiles is the per-ecosystem zip, not a live query and not `all.zip`. OSV documents `https://storage.googleapis.com/osv-vulnerabilities/<ECOSYSTEM>/all.zip`, individual `<ECOSYSTEM>/<ID>.json` files, and a reverse-chronological `modified_id.csv` so a client can stop at a timestamp it has already applied. The export is continuous. The data page presents that bucket, not `POST https://api.osv.dev/v1/query`, as the download ([OSV data sources](https://google.github.io/osv.dev/data/)). A full `all.zip` is the wrong default for a small scanner: on 12 November 2026 its `Content-Length` was **2,940,295,302** bytes, against **220,559,266** for `npm/all.zip`, and those sizes are that day’s objects, not a published estimate. There is no single license for the aggregate. Named upstreams include CC-BY 4.0 (GitHub Advisory Database, PyPI, Go, OSS-Fuzz), CC0 1.0 (Rust), CC-BY-SA 4.0 (Ubuntu, Alpine), and CC-BY-NC-ND 4.0 plus a separate commercial term (Chainguard/Wolfi) ([OSV data sources](https://google.github.io/osv.dev/data/)). Shipping only the ecosystems Chaca will match avoids that mix. The GitHub git mirror (`github/advisory-database`, CC-BY 4.0) is redundant for ranges OSV already ingested, and it is the better copy only if a consumer needs `database_specific` or a review flag the OSV evaluation algorithm ignores. GitHub warns the mirror layout can change incompatibly, and it does not state a refresh interval. EPSS on that database is synchronized daily, so a clone goes stale on that field even when the range does not ([advisory-database README](https://github.com/github/advisory-database/blob/main/README.md)).

Vendor HTML is the primary bound for the five products a banner can name, because that is where the version numbers match the fingerprint. nginx.org states, for CVE-2021-23017, “Not vulnerable: 1.21.0+, 1.20.1+” and “Vulnerable: 0.6.18-1.20.0,” and for CVE-2026-15176, “Not vulnerable: 1.31.7+, 1.30.6+” and “Vulnerable: 0.1.29-1.31.6.” The page does not say whether the hyphen is inclusive, and it links no JSON feed or license ([nginx security advisories](https://nginx.org/en/security_advisories.html)). OpenSSL’s vulnerability index uses “from A before B”: CVE-2026-88823, published 10 November 2026, is affected “from 4.1.0 before 4.1.1,” “from 4.0.0 before 4.0.4,” and “from 3.5.0 before 3.5.10,” with a plaintext file at `https://openssl-library.org/news/secadv/20261110.txt` rather than a database ([OpenSSL vulnerabilities](https://openssl-library.org/news/vulnerabilities/)). Apache’s 2.4 page says CVE-2026-119618 “Affects 2.4.55 through 2.4.70” and was fixed in 2.4.71, released 2026-11-11, while CVE-2026-42528 only “Affects through 2.4.68.” A question mark means the affected version was not verified, and a “-dev” fix is not a release ([Apache HTTP Server 2.4 vulnerabilities](https://httpd.apache.org/security/vulnerabilities_24.html)). WordPress names fixed branch releases in posts, not in a range file: the 17 July 2026 post says versions prior to 6.8 are not affected by that release’s issue, 6.9 is fixed in 6.9.5, and 6.8 is fixed in 6.8.6 ([WordPress 7.0.2](https://wordpress.org/news/2026/07/wordpress-7-0-2-release/)). The project’s own rule is that only the newest WordPress version is actively supported and that backports are a courtesy ([Make WordPress Secure, 18 June 2025](https://make.wordpress.org/security/2025/06/18/security-updates-will-cease-for-wordpress-versions-4-1-through-4-6/)). PHP’s machine-readable-looking page is a support window — two years of full support, then two years of critical fixes only — and the per-branch dates in the fetched table were column-shifted, so they are not usable. A WordPress.org post on 21 October 2026 says versions of PHP prior to 8.2 no longer receive security updates from the PHP project. That is WordPress repeating a cutoff, not a PHP CVE map ([PHP supported versions](https://www.php.net/supported-versions.php); [WordPress news, 21 October 2026](https://wordpress.org/news/2026/10/critical-php-security-release/)).

NVD is a secondary index, and after 15 April 2026 it is an incomplete one. NIST still lists every submitted CVE, but product-list enrichment is scheduled only for CISA KEV, software used in the federal government, and critical software under EO 14028. Everything else is “Lowest Priority - not scheduled for immediate enrichment.” Backlog CVEs with an NVD publish date earlier than 1 March 2026 moved to “Not Scheduled,” except KEV. NIST also stopped routinely adding its own severity score when the CNA already provided one. Submissions rose **263%** from 2020 to 2025; NIST enriched nearly **42,000** CVEs in 2025; first-quarter 2026 submissions were nearly one-third higher than the same quarter of 2025 ([NIST, 15 April 2026](https://www.nist.gov/news-events/news/2026/04/nist-updates-nvd-operations-address-record-cve-growth)). The public API limit is **5 requests in a rolling 30-second window** without a key and **50** with a key, and NIST tells clients to sleep between calls ([NVD start here](https://nvd.nist.gov/developers/start-here)). No 2026 NIST page retrieved here says whether the legacy JSON zip feeds are still served. The 2022 retirement plan, an archived October 2024 timeline, and a Fraunhofer FKIE reconstruction disagree, and FKIE’s year files are an unofficial mirror that says it is not endorsed by NVD ([NIST feed announcement](https://nvd.nist.gov/General/News/changes-to-feeds-and-apis); [fkie-cad/nvd-json-data-feeds](https://github.com/fkie-cad/nvd-json-data-feeds)). The terms page retrieved does not name a license. Do not call NVD public domain, and do not vendor the FKIE files as NVD.

CVE JSON 5 is the daily offline archive of the prose and the structured `lessThan` fields, not a replacement for the vendor line. The CVE Program tells a daily job to take `Year-Month-Day_all_CVEs_at_midnight.zip`, which stays unchanged for 24 hours, and an hourly job to take the delta zip. The git repo tracks the CVE Services API about every seven minutes. The downloads page says the zips are large and does not give a byte size; `main.zip` returned no `Content-Length`. Legacy CSV, HTML, XML, and CVRF ended 30 June 2024. The program’s terms of use were pointed at and not opened, so no license name is stated here ([CVE downloads](https://www.cve.org/downloads); [CVEProject/cvelistV5](https://github.com/CVEProject/cvelistV5)). Among records published in 2026 through 7 September, one analyst counted an affected-version range on **100%** of GitHub CNA records (n=9,599) and on **14%** of MITRE-as-CNA-of-last-resort records (n=2,918). Those are the author’s counts, not a CVE Program statistic ([Cloud Security Partners, 6 November 2026](https://www.cloudsecuritypartners.com/blog/nobody-waits-for-your-project-to-be-ready-for-its-first-cve)). Debian, Ubuntu, and Alpine OSV data answer a third question — whether a distro package is affected — and that package string is not an upstream banner.

| What Chaca matched | Offline artifact to keep | What it will not do |
| --- | --- | --- |
| npm, crates.io, Go, and any other registry GitHub actually reviews | That ecosystem’s OSV `all.zip`, refreshed with `modified_id.csv` | Replace the vendor page for nginx, OpenSSL, httpd, PHP, or WordPress |
| Those five upstream products | A snapshot of the vendor HTML or OpenSSL `secadv` text, taken by Chaca | Appear in `ecosystems.txt` as of 12 November 2026 |
| A CPE interval, when NIST enriched one | A local cache filled on a schedule inside the 5/50-per-30-seconds limit | Ship as a zip NIST currently tells you to vendor |
| CNA prose and real `lessThan` bounds | The CVE List midnight baseline | Turn a sentence in `versions[].version` into a range |

## A banner version is the wrong package key

The four composition scanners identify a product, then compare versions with that ecosystem’s ordering. Grype accepts a PURL or a CPE the operator already built, checks PURL format first, and turns CPE matching off by default for java, dotnet, golang, javascript, python, ruby, rust, hex, and dpkg. A 2026 change maps selected CPEs onto package specifiers specifically to avoid what the author calls a false-positive tsunami from full CPE matching ([Grype configuration](https://oss.anchore.com/docs/reference/grype/configuration/); [anchore/grype#3332](https://github.com/anchore/grype/pull/3332)). Grype’s version formats, on the main branch as fetched 12 November 2026, are Unknown, Semantic, Apk, Deb, Maven, RPM, Python, KB, Gem, Portage, Go, JVM, Bitnami, and Pacman. There is no constant named `generic` or `semver` ([grype/version/format.go](https://raw.githubusercontent.com/anchore/grype/main/grype/version/format.go)). Trivy selects the OS vendor advisory for packages installed by `dpkg`, `yum`, `apk`, and similar, because “OS vendors usually backport upstream fixes, and the fixed version can be different from the upstream fixed version.” A language package whose version is a range is skipped unless comprehensive mode uses the minimum, which the docs say can add false positives ([Trivy vulnerability scanning](https://github.com/aquasecurity/trivy/blob/main/docs/guide/scanner/vulnerability.md)). osv-scanner prefers a resolved lockfile and says a manifest “may not be the version that is installed” ([OSV-Scanner usage](https://google.github.io/osv-scanner/usage/)). Dependency-Check does the reverse of a version compare: it guesses a CPE from file evidence and attaches the NVD CVEs for that CPE. Confidence equals the lowest evidence score used. The internals page describes no semver, deb, rpm, apk, or maven comparator ([How does dependency-check work?](https://dependency-check.github.io/DependencyCheck/general/internals.html)).

None of those pages describe an HTTP `Server`, `X-Powered-By`, or generator banner. The sentence “a banner version is not sufficient” does not appear in them. The closest written limits are Trivy’s refusal to score a non-unique version and osv-scanner’s warning about unpinned manifests. A token such as `nginx/1.28.0` or `Apache/2.4.41 (Ubuntu)` has no Debian revision and no RPM epoch-release. Feeding it to Grype as a CPE is a documented interface and, given those tools’ own backport notes, the match path Grype disables by default for dpkg. The banner-specific evidence is elsewhere. nginx documents two branches: mainline has an odd middle number and is updated about every one or two months; stable has an even middle number, is updated about once a year or as needed, and receives security fixes “that are always backported from the Mainline version.” Distribution packages may be outdated, F5 does not verify their contents, and many long-term-support distributions ship only stable ([Installing NGINX Open Source](https://docs.nginx.com/nginx/admin-guide/installing-nginx/installing-nginx-open-source/)). OpenSSL’s 1.1.1 end-of-life post says a copy from an OS vendor can have a different support period and tells the reader to check that vendor ([OpenSSL 1.1.1 End of Life](https://www.openssl.org/blog/blog/2023/09/11/eol-111)). A third-party lab, on one Ubuntu 26.04 host, reported that all 16 advisories from a version-only nginx check were already patched or not affected in the distro package. That is one author’s one-host reading, the ranges were not re-checked against NVD, and it is not a false-positive rate for Grype, Trivy, osv-scanner, or Dependency-Check ([damonsec, 31 October 2026](https://www.damonsec.com/blog/check-nginx-version-vulnerable-backports)).

The same CVE is stored three ways, and the notes do not claim they are equivalent. CVE-2021-23017’s CVE JSON 5.1 record has no `lessThan`, no `lessThanOrEqual`, and no `versionType`. Its only version field is the sentence “Nginx Web Server versions 0.6.18 thru 1.20.0 before 1.20.1…” ([CVE AWG record](https://cveawg.mitre.org/api/cve/CVE-2021-23017)). The NVD 2.0 payload copies that sentence into `affectedData` and, separately, stores `cpe:2.3:a:f5:nginx:*:*:*:*:*:*:*:*` with `versionStartIncluding` **0.6.18** and `versionEndExcluding` **1.20.1**. The same configuration list also matches OpenResty, Fedora 33 and 34 with no range, and Oracle and NetApp products ([NVD CVE API](https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=CVE-2021-23017)). nginx.org’s “Not vulnerable” pair is a third wording, and it is a branch pair, not one line. A matcher that keys only on the CVE id, or that treats an `OpenSSL/` token on an Apache `Server` line as the server package, crosses products the way Dependency-Check attaches a server CPE to a client library and the way Grype can hang every source-package CVE on a binary built from that source ([How to read the reports](https://dependency-check.github.io/DependencyCheck/general/thereport.html); [Anchore community thread](https://anchorecommunity.discourse.group/t/indirect-matches-vulnerabilities-affecting-the-upstream-packages-are-sometimes-too-broad/523)).

Chaca therefore needs three comparators, not a scheme named `generic`. OSV schema 1.9.2 (13 October 2026) evaluates `SEMVER` with SemVer 2.0.0 ordering and no leading `v`, `ECOSYSTEM` as uninterpreted ecosystem strings that a generic client may be unable to order, or `GIT` with full commit hashes and a commit graph. A version is vulnerable at or after `introduced` and strictly before `fixed`. `last_affected` is an inclusive ceiling and the schema says it can false-negative, so `fixed` is preferred. `introduced: "0"` sorts before every other version. The spec recommends an enumerated `versions` list for `ECOSYSTEM` ranges; osv.dev fills that list for supported ecosystems when it can ([OSV schema](https://ossf.github.io/osv-schema/)). CVE JSON 5, when the CNA actually uses the fields, means `version` ≤ V < `lessThan`, or `version` ≤ V ≤ `lessThanOrEqual`, and `versionType` is required because order is not universal. `CVE-2026-108142` does this with `versionType` `semver`. CVE-2021-23017 does not. Kernel records add a fourth trap: `versionType` `git` carries commit hashes beside a separate semver block, and a naive numeric compare of kernel versions is the mistake Bootlin’s checker was changed to avoid. That comparer is the wrong one for nginx, OpenSSL, and httpd even though both use CVE ids ([CVE schema versions.md](https://raw.githubusercontent.com/CVEProject/cve-schema/main/schema/docs/versions.md); [Bootlin](https://bootlin.com/blog/sbom-cve-check-1-4-0-released/)). GitHub’s REST field `vulnerable_version_range` is a string such as `>= 13.4.2, < 13.6.5` with a separate `first_patched_version`. Files in the git mirror are OSV events, plus an optional `database_specific.last_known_affected_version_range` that consumers are told not to rely on. Code that reads one must not assume the other is present ([REST: global security advisories](https://docs.github.com/en/rest/security-advisories/global-advisories); [advisory-database README](https://github.com/github/advisory-database/blob/main/README.md)).

The finding shape those tools already share is the one to emit, and it does not include exploit steps. Grype prints the vulnerability id, the installed version, and FIXED-IN as the fixing version, the text `(won't fix)`, or empty when no fix is available. An empty FIXED-IN is still a row. Default npm ids can be GHSA ids. Severity labels include Critical, High, Medium, Low, Negligible, and Unknown ([Understanding Grype results](https://oss.anchore.com/docs/guides/vulnerability/interpreting-results/)). Trivy takes severity from the selected source, not from NVD by default: CVE-2023-0464 is HIGH in NVD and Low in Red Hat, and Trivy shows Low. A row with no fixed version stays `affected` unless the vendor supplied another status. `--ignore-unfixed` is a filter, not a claim that the record is safe ([Trivy vulnerability scanning](https://github.com/aquasecurity/trivy/blob/main/docs/guide/scanner/vulnerability.md)). osv-scanner prints the OSV URL, the installed version, and `--` when there is no fix ([OSV-Scanner output](https://google.github.io/osv-scanner/output/)). For a banner, add what those tables assume and a header does not have: the source of the bound, and a confidence label modeled on Dependency-Check’s “check the CPE before you trust the CVEs.” The label is “upstream version string, not a distro package.” Do not invent a severity the vendor page or the matched advisory did not state.

End of life is not that row. OpenSSL 1.1.1 reached public end of life on 11 September 2023, and the final public release named for the series was 1.1.1w. OpenSSL Library 3.0 reached end of life on 7 September 2026. The roadmap, which says its dates can change, also marks 3.6 non-LTS as supported until 1 November 2026 and therefore already ended by this report’s date, while 3.5 LTS runs until 8 April 2030, 4.0 until 14 May 2027, and 4.1 until 23 November 2027 ([OpenSSL roadmap](https://openssl-library.org/roadmap/); [OpenSSL 3.0 End of Life](https://openssl-library.org/post/2026-09-16-eol30/)). No Grype, Trivy, osv-scanner, or Dependency-Check page reviewed here emits a finding only because a branch is end of life. Absence of that sentence is not a written promise that they never will. It is enough to refuse an EOL-only row: after public end of life the matcher keeps reporting 3.0 only where an existing advisory’s range still contains the detected version. Paid extended support is not a public release stream, so a version number cannot separate a commercially patched 3.0 from an unpatched 3.0. The upgrade to print is the end of the vendor line that contains the detected version — 4.1.1 on a 4.1 banner, 3.5.10 on a 3.5 banner — not a jump to a newer major, and not “unsupported, therefore vulnerable.”

Ranges also move. Kernel.org’s CNA updates entries, including revocations and tighter ranges, and tells consumers who read a CVE once and never refresh that they are wrong ([Greg Kroah-Hartman, 31 January 2025](https://social.kernel.org/notice/AqeMuSrRtRMdXOSRQ8)). Apache’s missing start bound and unverified “?” are the same class of hole inside the web-server page. A snapshot that never refreshes will keep the old bound. Severity lag is real and is not what this matcher should read. A November 2025 summary of a Sonatype report says 62% of open-source CVEs that year had overstated severity and that the average wait for an NVD score was six weeks; the underlying PDF was not opened, so those figures are not used as version bounds ([Expert Insights](https://expertinsights.com/news/research-reveals-major-flaws-in-cve-program)). An academic count that was opened is about identity, not scores: 50.18% of vendor names in NVD CPEs were inconsistent ([arXiv:2505.13895](https://arxiv.org/html/2505.13895v1)). CSO Online, reporting the Commerce inspector general, says NIST had no sustainable process for NVD submissions and had not cleared the backlog. The figures of about 13,000 at the start of June 2024 and over 27,000 by the end of 2025 come from a mirrored PDF, not from a page retrieved at `oig.doc.gov`, so they stay unverified ([CSO Online](https://www.csoonline.com/article/4181438/us-government-report-slams-nist-for-nvd-backlog.html)).

## Header-only work is cookie prefixes, not new attacks

Chaca already reports security headers at a high level. The sourced gap is not another injection check. It is the small set of decisions one response’s headers can still settle, measured against ZAP’s release rules, MDN HTTP Observatory algorithm version 6, and ASVS 5.0.0. Observatory runs exactly twelve tests: Content-Security-Policy, cookies, Cross-Origin-Embedder-Policy, Cross-Origin-Opener-Policy, Cross-Origin Resource Sharing, redirection, Referrer-Policy, Strict-Transport-Security, Subresource Integrity, X-Content-Type-Options, X-Frame-Options, and Cross-Origin-Resource-Policy ([constants.js](https://raw.githubusercontent.com/mdn/mdn-http-observatory/main/src/constants.js)). The July 2024 launch post says the migrated Observatory dropped X-XSS-Protection and the Flash and Silverlight cross-domain policy tests, does not grade TLS or certificates, and that an A+ is not a claim of freedom from injection or outdated software ([MDN HTTP Observatory launch](https://developer.mozilla.org/en-US/blog/mdn-http-observatory-launch/)). ZAP’s matching XSS-protection alert and its Apache Range header denial-of-service alert are deprecated ([ZAP alert details](https://www.zaproxy.org/docs/alerts/)). The passive intersection worth keeping in a default profile is HTTPS with no mixed content, HSTS with a long `max-age`, a CSP, a framing control, `nosniff`, Referrer-Policy, CORS that is not `*` on a sensitive response, and `Secure` on cookies.

ASVS levels change which of those are failures. HSTS on every response with `max-age` of at least one year is 3.4.1 at Level 1. `includeSubDomains` is Level 2, and preload of the apex is Level 3. TLS for every external client connection, with no cleartext fallback, is 12.2.1 at Level 1. Only recommended TLS versions, “such as TLS 1.2 and TLS 1.3,” with the latest preferred, is 12.1.1 at Level 1; 1.0 and 1.1 are not in that list. `Access-Control-Allow-Origin` must not be `*` on a response that carries sensitive data (3.4.2, Level 1), and every cookie must have `Secure` (3.3.1, Level 1) ([ASVS 5.0.0 V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md); [ASVS 5.0.0 V12](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x21-V12-Secure-Communication.md)). CSP that limits script execution, `frame-ancestors`, `nosniff`, Referrer-Policy, HttpOnly where script must not read the value, and SameSite matched to purpose are Level 2. A third-party walkthrough that calls `nosniff` Level 1 and `Permissions-Policy` an ASVS requirement contradicts the tagged 5.0.0 text: `nosniff` is 3.4.4 at Level 2, and V3.4 does not mention Permissions-Policy ([ASVS 5.0.0 V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md)). ASVS also says `X-Frame-Options` is obsolete and “may not be relied upon,” while ZAP still ships a release alert for a missing anti-clickjacking header and Observatory still runs an `X-Frame-Options` test that an explicit `frame-ancestors` can pass. Report `frame-ancestors` as the control and `X-Frame-Options` as the legacy header those scanners still score. Observatory’s current point values, and whether a missing COOP fails the grade or only loses a bonus, were not read. ZAP’s CSP “Header & Meta” alert 10055-12 is still on the public table fetched 12 November 2026, but the passive-rules changelog of 25 September 2026 says that alert is no longer raised. Do not treat the table row as proof it fires ([pscanrules changelog](https://www.zaproxy.org/docs/addons/pscanrules/changelog/)).

The 2025–2026 addition that is both new and header-only is the cookie prefix. ASVS 5.0.0, released May 2025, requires at Level 1 that a cookie use `__Secure-` when its name does not use `__Host-`, and at Level 2 that it use `__Host-` unless it is explicitly shared with other hosts. ZAP’s release cookie rules fetched on 12 November 2026 have no prefix alert. Observatory’s cookie test does not look at prefixes. It treats a name containing `login` or `sess` as a session cookie and a name containing `csrf` as an anti-CSRF cookie, and it fails a session cookie without `Secure` or `HttpOnly` ([ASVS 5.0.0 V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md); [cookies.js](https://raw.githubusercontent.com/mdn/mdn-http-observatory/main/src/analyzer/tests/cookies.js)). The newer `__Host-Http-` / `__Http-` prefixes are an open ASVS issue from 12 February 2026, not a change to 5.0.0 ([OWASP/ASVS issue 3331](https://github.com/OWASP/ASVS/issues/3331)). COOP is an ASVS Level 3 requirement on HTML responses. CORP is one Level 3 option for stopping credentialed cross-origin loads. COEP is in Observatory version 6 and in a ZAP beta rule, and it is not a numbered ASVS 5.0.0 V3 requirement. Permissions-Policy is a ZAP beta rule and is in neither ASVS 5.0.0 V3.4 nor Observatory’s twelve tests. No primary source reviewed here names a Browsing Topics check. The launch post’s narrative list names CORP and not COOP; the current `constants.js` includes COOP, and the current file is what the tool runs. Report COOP, COEP, CORP, and Permissions-Policy as informational unless the scan is explicitly scoring ASVS Level 3.

Version banners stay in the report and stay out of the Level 1 fail set. ZAP’s release passive rules flag a product in `Server` as informational and a version in `Server` as low, and they flag `X-Powered-By`, `X-Backend-Server`, `X-AspNet-Version`, `X-Debug-Token`, and `X-ChromeLogger-Data`. A separate release passive rule scores PHP and Apache HTTP Server version strings as high when known-vulnerable and low when only possibly vulnerable ([ZAP alert details](https://www.zaproxy.org/docs/alerts/)). ASVS 13.4.6, “does not expose detailed version information of backend components,” is Level 3, not Level 1. Failing a build for `Server: nginx` with no version is stricter than ASVS 5.0.0 Level 1 ([ASVS 5.0.0 V13](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x22-V13-Configuration.md)). The notes never document a matcher that starts from a generator token. Treat a generator string the way the other banners are treated: an identity hint whose upgrade, for WordPress core, is the fixed release the WordPress post names for that branch. If the post gives no per-branch number — the 22 September 2026 post says the fix was backported “currently through 4.7” without one in the excerpt — do not invent one ([WordPress 7.1.2](https://wordpress.org/news/2026/09/wordpress-7-1-2-release/)). Security updates for WordPress 4.1 through 4.6 stopped in July 2025. That cutoff is a support boundary, the same class as OpenSSL’s public end of life, not a CVE range ([dropping 4.1–4.6](https://wordpress.org/news/2025/06/dropping-security-updates-for-wordpress-versions-4-1-through-4-6/)).

Everything else the catalogs still care about is a second ordinary GET or a handshake, not a header decision and not an attack payload. `security.txt` must be fetched from `/.well-known/security.txt` over HTTPS. `Contact` and a single `Expires` are required; the RFC recommends an expiry less than a year out; a `Canonical` that does not list the retrieval URL means the file should not be trusted. WSTG-INFO-03 tells testers to retrieve it, along with `robots.txt`, sitemaps, and `humans.txt`. ZAP’s “security.txt observed” alert is beta and means the file was seen, not that it is missing or stale ([RFC 9116](https://www.rfc-editor.org/rfc/rfc9116.html); [WSTG-INFO-03](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/01-Information_Gathering/03-Review_Webserver_Metafiles_for_Information_Leakage/)). TLS version, cipher, certificate trust, OCSP stapling, Encrypted Client Hello, and a hybrid post-quantum group are handshake properties. ASVS 12.1.1 does not mention hybrid or ML-KEM. The ZAP alert table has no post-quantum rule. Observatory does not inspect TLS. WSTG text that prefers TLS 1.3 for post-quantum compatibility, and that names hybrid constructions during the transition, comes from a search index of an OWASP URL. A direct fetch of the matching `wstg.owasp.org` slug on 12 November 2026 returned 404, so that paragraph is index evidence. OWASP Quantum Top 10 QS06 describes operator monitoring of the negotiated group, not a ZAP or Observatory passive rule. Do not fail a default scan for lack of a hybrid group ([QS06](https://github.com/OWASP/quantum-security-project/blob/main/quantum-top-10/QS06_Insecure-Migration-and-Hybrid-Misuse.md)). DNS CAA, DNSSEC, SPF, DKIM, and DMARC appear in none of the four baseline sources. HSTS preload membership needs the preload list. Whether an `Origin` was reflected cannot be decided without a second request that sets `Origin`; a `*` or a reflected value on the one response is a lead, not a confirmed credentialed read.

Default scope stays on that non-destructive side. ZAP says proxying and passive scanning do not themselves attack the application, that active scanning may create, change, or delete data, and that spidering can cause problems especially if it submits POST. Nuclei excludes templates tagged `fuzz` and `dos` from the default scan and runs them only with an explicit include. Burp’s “Audit checks - passive” configuration selects issues detected from normal requests and responses. Medium-active checks can log users out or trigger alerts. Intrusive checks can modify data. Time-based methods exist as a class that can be turned off because they force timeouts. The fetched Burp page does not say an unmodified new scan already excludes intrusive checks, so that stronger claim is not available. None of the three policy pages use the words “credential stuffing.” The sourced rule is still to keep data-changing and denial-of-service checks behind an opt-in, and to require authorization before anything beyond looking at traffic the operator is allowed to see ([ZAP scanning FAQ](https://www.zaproxy.org/faq/is-there-any-danger-when-scanning-with-zap-against-a-live-website-e-g-create-delete-update-corrupt-data/); [Nuclei FAQ](https://docs.projectdiscovery.io/opensource/nuclei/faq); [Burp built-in configurations](https://portswigger.net/burp/documentation/scanner/scan-configurations/burp-scanner-built-in-configs)). Chaca’s existing active injection, SSRF, and authentication tests belong in that opt-in, not in the header pass this report is specifying. Path discovery for admin panels, `.git`, and actuators is a further GET of a well-known URL. ASVS wants `.git` and `.svn` inaccessible at Level 1, but ZAP’s source-control rules are beta and active, not release passive. That work is discovery, and it is not decidable from the page already fetched.

## Published defaults do not define a safe rate

ZAP, Nuclei, and Burp all separate a concurrency cap from a send-rate or an inter-request delay, and none of them publish one universal safe rate. Nuclei is the only one of the three that ships numbers for both: `-c` and `-bulk-size` default to **25**, and `-rate-limit` defaults to **150 HTTP requests per second**, global. The same page sets HTTP timeout to **10 seconds**, retries to **1**, and `-max-host-error` to **30** network errors before the host is dropped. Headless bulk size and concurrency default to 10, JavaScript runtime concurrency to 120, and payload concurrency to 25. Template-spray, the default, is described as the strategy that does not aggressively scan a single target, and it uses more memory because each template holds its own target chunk. The docs say there is no out-of-the-box optimum and that `-c`, `-bs`, and `-rl` have to be fit to the scanner and the targets ([Mass Scanning with Nuclei](https://docs.projectdiscovery.io/opensource/nuclei/mass-scanning-cli)). Copying 150 per second or a width of 25 is not a target-safety recommendation from ZAP or Burp.

ZAP’s rate-limit page gives every rule a requests-per-second maximum and does not publish a default rule or a default number. The most restrictive matching rule wins. “Delay When Scanning” is deprecated because a sleep does not enforce a rate once many threads are in flight; the docs point operators at the rate-limit rule instead ([ZAP Rate Limit](https://www.zaproxy.org/docs/desktop/addons/network/options/ratelimit/); [ZAP Options Active Scan](https://www.zaproxy.org/docs/desktop/ui/dialogs/options/ascan/)). In ZAP 2.17.0 source the fallback for hosts scanned at once is **2**. Threads per host fall back to `Constant.getDefaultThreadCount()` with a floor of 1. A closed 2.13 issue says the default thread count should be the number of available processors. That method was not opened, so the live integer is not established ([ScannerParam.java](https://fossies.org/dox/zaproxy-2.17.0/ScannerParam_8java_source.html); [zaproxy#7663](https://github.com/zaproxy/zaproxy/issues/7663)). Connection and read timeout default to **20 seconds** ([ZAP Connection options](https://www.zaproxy.org/docs/desktop/addons/network/options/connection/)). Burp’s resource pool can set a maximum number of concurrent requests and a millisecond delay, including a random variation, and it can add a short delay on **429**, **503**, or other codes the user lists. Throttling on `200` “could result in significantly decreased scan performance.” No numeric default for either pool control is stated. The DAST text’s worked example of “up to 50%” variation is a 500 ms interval moving between 250 and 750. The per-machine “Concurrent scan limit” of **1** on a new scanning machine caps scans, not HTTP requests inside a scan ([Burp Tasks settings](https://portswigger.net/burp/documentation/desktop/settings/project/tasks); [Custom scan configuration](https://portswigger.net/burp/documentation/dast/user-guide/reference/custom-scan-config-settings)).

reqwest 0.12.28 will not supply the missing bound. `timeout`, `read_timeout`, and `connect_timeout` default to no timeout. `pool_idle_timeout` defaults to **90 seconds**. `pool_max_idle_per_host` defaults to `usize::MAX`. The 30-second combined timeout in reqwest 0.9 is not what 0.12.28 documents ([reqwest 0.12.28 client.rs](https://docs.rs/reqwest/0.12.28/src/reqwest/async_impl/client.rs.html)). No current reqwest document fetched here states a default cap on active, as opposed to idle, connections per host. On HTTP/2, raising the idle-pool cap does not create more parallel streams to one host. The server’s `SETTINGS_MAX_CONCURRENT_STREAMS` limits streams the client may open. The setting starts unlimited, and the specification recommends it be no smaller than 100. hyper’s client-side `max_concurrent_streams` limits streams the remote peer opens, not streams the caller opens. hyper’s server default advertisement is 200 and is explicitly unstable ([RFC 9113](https://www.rfc-editor.org/rfc/rfc9113); [hyper client http2.rs](https://github.com/hyperium/hyper/blob/master/src/client/conn/http2.rs)). Initial stream and connection flow-control windows are **65,535** octets until the peer raises them. For one origin, many in-flight requests share one TCP connection up to that server cap. One TCP connection per in-flight request is the HTTP/1 pattern the RFC describes. No source fetched here says whether reqwest opens a second HTTP/2 connection when the first hits the server’s stream limit. `crawl-delay` is not a rule to implement: Google says it does not support that field, and this pass did not find it in the retrieved sections of RFC 9309 ([Google robots.txt](https://developers.google.com/crawling/docs/robots-txt/robots-txt-spec)).

The limiter and the in-flight cap answer different questions, and the expensive object has to be created after both are held. `golang.org/x/time/rate` is a token bucket. `Wait` blocks until a token is available or the context is canceled. `Reserve` accounts for the reservation immediately and tells the caller how long to sleep. Callers who must respect cancellation are told to use `Wait`, not `Reserve` plus an unbounded sleep ([rate.go](https://github.com/golang/time/blob/master/rate/rate.go)). Nuclei applies its global limit “just before sending,” after the requests “are already prepared and are in memory waiting to be sent,” so a very low rate raises memory as well as lowering throughput ([Mass Scanning with Nuclei](https://docs.projectdiscovery.io/opensource/nuclei/mass-scanning-cli)). No Tokio or reqwest document was found that orders a semaphore permit against a rate reservation. The order below is inferred from that Go contract and from Nuclei’s warning, not from a Rust HTTP guide. Take the token immediately before the socket write, on a worker that already holds one in-flight slot. Do not hold the decision lock across the response read, or the configured concurrency collapses to one request at a time. If the wait is abandoned, the reservation must not stay outstanding. The `Reservation.Cancel` body text was not re-read in this pass, so the exact restore rules are not quoted. Independent GETs are the phase these products already parallelize. A later request whose URL, cookie, or token comes from an earlier response stays ordered. ZAP’s spider is multi-threaded and uses a shared visited-set. It is not a single ordered walk. Backing off when the target returns 429 or 503 is the behavior Burp documents. Whether ZAP’s own RPS rule is a token bucket, and whether it blocks a thread or queues a message, is not stated on the rate-limit page.

Body caps are the memory control the sources actually state. Nuclei’s current mass-scanning page says `-response-size-read` defaults to **4 MB** so a large object is not stored whole, and it states a heap relationship of **1–1.5× (concurrency × response-size-read)**. No workload or measurement procedure is given, and the page does not say whether “concurrency” means `-c`, `-bs`, or the product of the two. Treat the factor as a vendor estimate. Do not conflate the read cap with the save cap. On 3 January 2024 a maintainer’s help text showed a read default of 10,485,760 and a save default of 1,048,576. An April 2024 bug log showed the engine’s `maxBodylimit` at 4,194,304 before later overwrites. The 2026 page is the current documented read default. The 2024 help line is not ([Mass Scanning with Nuclei](https://docs.projectdiscovery.io/opensource/nuclei/mass-scanning-cli); [discussion #4589](https://github.com/orgs/projectdiscovery/discussions/4589); [nuclei#5094](https://github.com/projectdiscovery/nuclei/issues/5094)). ZAP’s spider automation job documents `maxParseSizeBytes` default **2,621,440**. The desktop spider page says zero means unlimited and does not give that integer, so the desktop default was not confirmed ([ZAP Spider Automation](https://www.zaproxy.org/docs/desktop/addons/spider/automation/)). No 2024–2026 writeup with a stated measurement method was found for bytes of RAM per TLS connection. Protocol windows are not process RSS. Chaca’s existing analyzed-body cap is the control that matches these products. Stopping the read and dropping the rest is what makes the cap real. The RFC does not specify a scanner’s cutoff.

| --- | --- | --- |

| In-flight work | Nuclei defaults to 25 and 25. ZAP 2.17.0 falls back to 2 hosts at once. Per-host threads were not confirmed beyond “processors” as intent and a floor of 1. | A single ZAP thread integer |

## Conclusion

The fingerprints Chaca already collects are an identity hint and, under ASVS, a Level 3 disclosure finding. They are not a vulnerability database. Writing another active check, or a comparer that sorts every banner with one semver function, would spend the next change on the two moves these sources refuse: scoring a non-unique upstream string as if it were a distro package, and sending something other than the response the scanner was already allowed to read. The database those fingerprints need is a small vendor snapshot plus OSV ecosystem zips, refreshed because ranges get tighter and because NVD will not fill the product list for a lowest-priority CVE. The performance model is already the one ZAP, Nuclei, and Burp describe. What reqwest will not do is choose the timeout, the body cap, or the moment the rate token is taken.

## What to build next

1. **Data source.** Vendor OSV `<ECOSYSTEM>/all.zip` only for registries Chaca will match, starting from `npm`, `crates.io`, and `Go`, and add Packagist, Maven, or PyPI only when those lockfiles are in scope. Refresh with `modified_id.csv`. Do not vendor `all.zip`, and do not call the OSV, NVD, or GitHub APIs on the scan path. For nginx, OpenSSL, Apache httpd, the PHP interpreter, and WordPress core, snapshot the vendor page (OpenSSL’s per-date `secadv` text included). Keep a scheduled NVD cache, inside 5 requests per 30 seconds or 50 with a key, as a secondary CPE index, and treat a missing `cpeMatch` as “no enriched bound,” not as “not affected.” Use the CVE List midnight zip for JSON 5 `lessThan` fields and for prose. Do not ship FKIE year files as NVD. Distro OSV records stay a separate identifier, used only when a distro package version is actually known.

2. **Matching rules.** Compare a version only with the ordering that record states: OSV `SEMVER` versus `ECOSYSTEM` versus an enumerated `versions` list; CVE JSON `lessThan` versus `lessThanOrEqual` versus a prose `version` that has neither; NVD `versionStartIncluding` / `versionEndExcluding` and the sibling fields. For nginx, stay inside the branch the middle number names and print that branch’s “Not vulnerable” version. Do not treat the hyphen as inclusive on both ends, because nginx.org does not say, and do not collapse nginx.org, the CNA sentence, and the NVD CPE interval into one range. For OpenSSL, use “from A before B” and report the fix on that line. For Apache, use a stated “through” end, refuse a missing start, and do not treat “?” or “-dev” as a confirmed fix. Do not match a `Server`, `X-Powered-By`, or generator token as a distro package, as a default-on CPE, or as an end-of-life finding. A header that names two products is two identities. Emit the advisory id, the detected version, the upgrade or an explicit no-fix, severity from that source, and a label that the version is an upstream banner. There is no scheme named `generic` to implement. Kernel git bounds are out of this comparer.

3. **Header-only checks.** On the headers of one response, add the ASVS Level 1 cookie prefix: `__Secure-` when the name is not `__Host-`. ZAP’s release rules and Observatory’s `cookies.js` do not score it. Confirm the existing header pass covers HSTS (`max-age` of at least one year before it counts as the Level 1 control), CSP including `object-src`, `base-uri`, and `frame-ancestors`, `X-Content-Type-Options: nosniff`, Referrer-Policy, `Access-Control-Allow-Origin` that is not `*` on a sensitive response, `Content-Type`, and `Set-Cookie` `Secure`, `HttpOnly`, and `SameSite`. Keep disclosure headers, including the `Server` and `X-Powered-By` fingerprints already collected, plus `X-AspNet-Version`, `X-Backend-Server`, `X-Debug-Token`, and `X-ChromeLogger-Data`, as informational at Level 1. Report COOP, COEP, CORP, and Permissions-Policy as informational. Do not fail the default scan for a missing hybrid post-quantum group, Browsing Topics, X-XSS-Protection, or a version-only `Server` token. Leave `security.txt`, `robots.txt`, TLS properties, and well-known path discovery as separate ordinary GETs. Do not add injection, SSRF, authentication-bypass, fuzzing, denial-of-service, or time-based checks to this default.

4. **Performance settings the sources state.** Keep a shared send-rate and a separate in-flight cap. Take the rate token immediately before the write, on a worker that already holds a slot, and build the body buffer only after both are held. Set a client timeout, because reqwest 0.12.28 documents none: Nuclei documents 10 seconds for HTTP, and ZAP documents 20 seconds for connection and read. Keep a body read cap: Nuclei’s current page documents 4 MB, and ZAP’s spider automation documents 2,621,440 bytes. Do not adopt Nuclei’s 150 requests per second or its width of 25 as a safety setting. ZAP publishes no default RPS, and the only host-concurrency integer confirmed in 2.17.0 source is a fallback of 2. Back off on 429 and 503, not on 200. On HTTP/2, multiplex on one connection up to the server’s stream limit. If a mass mode is added later, Nuclei’s other stated defaults are one retry and 30 host errors before the host is dropped. The idle pool, at 90 seconds with no per-host cap, enforces none of this. `crawl-delay` is not a setting these sources give you.
