# Defensive scanner checks, 2026

Scope: passive and configuration checks that OWASP ZAP, MDN HTTP Observatory, OWASP ASVS 5.0.0, and the current WSTG still treat as baseline, plus 2025–2026 additions those sources actually name. The product already covers security headers at a high level, CMS fingerprinting, exposed admin panels, API path discovery, data-pattern exposure, and active injection, SSRF, and authentication tests. This note is the check catalog those features should be measured against. No exploit payloads are included.

Primary versions used: ZAP alert catalog as published on zaproxy.org (page fetched 12 Nov 2026; release rules are the default set); MDN HTTP Observatory test list in `mdn-http-observatory` `ALGORITHM_VERSION = 6`; ASVS 5.0.0 requirement text at tag `v5.0.0` (PDF commit 9 Nov 2025; v5.0.0 itself was released May 2025); WSTG “latest” chapter WSTG-INFO-03 fetched 12 Nov 2026. ASVS 5.0.0 requirement tables do not carry a CWE column. A mappings note says CWE identifiers were removed before 5.0.0, so CWE below is cited only where ZAP prints one.

## Which passive checks do ZAP, HTTP Observatory, and ASVS or WSTG still treat as baseline?

### Takeaway

The shared baseline is still transport enforcement (HTTPS plus HSTS), a small header set (CSP, framing, `nosniff`, Referrer-Policy, CORS), cookie flags (Secure, HttpOnly on session cookies, SameSite), and information leakage in headers and HTML. TLS protocol and certificate quality are an ASVS Level 1 control and a WSTG cryptography test, but MDN HTTP Observatory deliberately does not grade them. DNS record hygiene (CAA, DNSSEC, email authentication) is not a baseline check in any of these four sources.

### Cited Findings

ZAP ships only `release` rules by default; beta and alpha rules are optional Marketplace add-ons. The alert table gives each release rule a CWE when the project assigned one. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/)

MDN HTTP Observatory `ALGORITHM_VERSION` 6 runs exactly these twelve tests: Content-Security-Policy, cookies, Cross-Origin-Embedder-Policy, Cross-Origin-Opener-Policy, Cross-Origin Resource Sharing, redirection, Referrer-Policy, Strict-Transport-Security, Subresource Integrity, X-Content-Type-Options, X-Frame-Options, and Cross-Origin-Resource-Policy. — [mdn-http-observatory constants.js](https://raw.githubusercontent.com/mdn/mdn-http-observatory/main/src/constants.js)

The July 2024 MDN launch post says the migrated Observatory removed the X-XSS-Protection test and the Flash/Silverlight `clientaccesspolicy.xml` and `crossdomain.xml` tests, added a Cross-Origin-Resource-Policy test, and retuned Referrer-Policy scoring. The same post says the new Observatory does not provide TLS or certificate data and had no plans to add it. An A+ grade is not a claim that the site is free of injection, outdated software, or password-storage flaws. — [Introducing the MDN HTTP Observatory](https://developer.mozilla.org/en-US/blog/mdn-http-observatory-launch/)

ZAP’s “Web Browser XSS Protection Not Enabled” (alert 10016) is marked deprecated, which lines up with Observatory dropping that test. ZAP’s “Apache Range Header DoS (CVE-2011-3192)” (alert 10053) is also deprecated. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/)

ASVS 5.0.0 applies to web applications, APIs, and web services. Levels are cumulative. Chapter V3 is browser-frontend only and “does not apply to machine-to-machine solutions.” — [ASVS 5.0.0 V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md); [arc42 summary of the May 2025 release](https://quality.arc42.org/standards/owasp-asvs)

A third-party ASVS walkthrough lists `X-Content-Type-Options` as Level 1 and `Permissions-Policy` as a Level 2 requirement. The tagged 5.0.0 text does not: `nosniff` is 3.4.4 at Level 2, and V3.4 does not mention Permissions-Policy. The official file is used below. — contradicted by [Reverse Polarity, 10 May 2026](https://reversepolarity.be/blog/asvs-5-v11-v12-v13-cryptography-tls-configuration-hardening/) against [ASVS 5.0.0 V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md)

WSTG latest still has an information-gathering chapter and a configuration-and-deployment chapter. The configuration index, as indexed for the OWASP site, still lists: network infrastructure, application platform configuration, file-extension handling, old backup and unreferenced files, admin interfaces, HTTP methods, HTTP Strict Transport Security, RIA cross-domain policy, subdomain takeover, cloud storage, Content Security Policy, path confusion, and other HTTP security header misconfigurations. — [WSTG 4.1 index](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/01-Information_Gathering/); [WSTG configuration index as indexed](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/02-Configuration_and_Deployment_Management_Testing/README)

Direct fetches on 12 Nov 2026 of the guessed `wstg.owasp.org` slugs for “Testing for Weak Transport Layer Security” and “Test Other HTTP Security Header Misconfigurations” returned “Page not found.” The configuration test list and the post-quantum TLS paragraphs below come from the search index of the OWASP URLs, not from a full-page fetch. Treat those two items as index-level evidence.

#### Transport

- **Cleartext HTTP / no downgrade.** ASVS 12.2.1 (Level 1): TLS for every client connection to external HTTP services, with no fallback to unencrypted communications. User impact: anyone on the path can read or change the session. ZAP “HTTP Only Site” (10106, CWE 311) is an active rule, not passive. Observatory’s redirection test checks that the first hop is HTTP to HTTPS on the same hostname before any further redirect, so HSTS can be learned; `http://example.com` → `https://www.example.com` is penalized. — [ASVS 5.0.0 V12](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x21-V12-Secure-Communication.md); [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [MDN Observatory launch](https://developer.mozilla.org/en-US/blog/mdn-http-observatory-launch/)
- **HSTS present, long-lived, and on HTTPS only.** ASVS 3.4.1 (Level 1): `Strict-Transport-Security` on all responses, `max-age` at least one year (the text requires “at least 1 year”); `includeSubDomains` from Level 2. Level 3 also wants the apex on the public preload list (3.7.4). ZAP release rule 10035 (CWE 319) covers header missing, `max-age=0`, duplicate headers, HSTS on plain HTTP, missing or malformed `max-age`, meta-defined HSTS, and malformed content. Observatory includes `strictTransportSecurityTest`. The current MDN test file’s minimum `max-age` was not opened for this note; do not assume the old “six months” score from the legacy Observatory API still applies. User impact: the browser will keep using HTTP, so a network attacker can strip TLS on the next visit. — [ASVS 5.0.0 V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md); [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [Observatory constants.js](https://raw.githubusercontent.com/mdn/mdn-http-observatory/main/src/constants.js)
- **Mixed content and insecure form targets.** ZAP release 10040 “Secure Pages Include Mixed Content” (CWE 311, low), 10041 “HTTP to HTTPS Insecure Transition in Form Post” (CWE 319, medium), 10042 “HTTPS to HTTP Insecure Transition in Form Post” (CWE 319, medium). User impact: a page that looks encrypted still loads or submits data in the clear. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- **TLS versions and cipher suites.** ASVS 12.1.1 (Level 1): only recommended versions, “such as TLS 1.2 and TLS 1.3,” with the latest preferred. TLS 1.0 and 1.1 are not in that list. ASVS 12.1.2 (Level 2): only recommended cipher suites, strongest preferred; Level 3 must be forward-secret only. ASVS points testers at the OWASP Transport Layer Security Cheat Sheet, Mozilla’s Server Side TLS guide, ssl-config.mozilla.org, and O-Saft. User impact: an old protocol or non-forward-secret suite lets a recorded session be decrypted later, or lets an on-path attacker downgrade the handshake. — [ASVS 5.0.0 V12](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x21-V12-Secure-Communication.md)
- **Service-to-service TLS** (ASVS 12.3.1–12.3.4, Level 2) is real but not visible to a single external page fetch. Not a default external-scanner check unless the scanner is placed on that path.

#### Headers

- **Content-Security-Policy.** ASVS 3.4.3 (Level 2): a CSP that limits script execution; minimum global policy includes `object-src 'none'` and `base-uri 'none'` and either an allowlist or nonces/hashes. Level 3 wants a per-response policy with nonces or hashes. Level 3 also wants a report sink (3.4.7). ZAP release 10038 “CSP Header Not Set” (CWE 693, medium) plus report-only and obsolete-header variants, and release 10055 policy-quality findings (CWE 693): obsolete `X-Content-Security-Policy` / `X-WebKit-CSP`, wildcards, `script-src`/`style-src` `unsafe-inline`, `unsafe-hashes`, `unsafe-eval`, malformed non-ASCII policy, invalid meta directive, and a directive with no fallback. Observatory includes `contentSecurityPolicyTest`. WSTG’s configuration index still lists “Test for Content Security Policy.” User impact: injected HTML can run script and load attacker-controlled objects. — [ASVS V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md); [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [Observatory constants.js](https://raw.githubusercontent.com/mdn/mdn-http-observatory/main/src/constants.js)
- **Framing / clickjacking.** ASVS 3.4.6 (Level 2): `frame-ancestors` on every response so embedding is denied by default. The requirement says `X-Frame-Options` is obsolete and “may not be relied upon.” ZAP still ships release 10020 “Missing Anti-clickjacking Header” and malformed or duplicated XFO (CWE 1021, medium). Observatory still runs `xFrameOptionsTest`, and the launch FAQ says an explicit CSP `frame-ancestors` passes that test even if framing is allowed. User impact: another site can overlay the real UI and capture clicks. — [ASVS V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md); [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [MDN Observatory launch](https://developer.mozilla.org/en-US/blog/mdn-http-observatory-launch/)
- **X-Content-Type-Options: nosniff.** ASVS 3.4.4 (Level 2), including because it enables Cross-Origin Read Blocking. ZAP release 10021 (CWE 693, low). Observatory runs `xContentTypeOptionsTest`. User impact: the browser may treat a user-controlled response as script or HTML. — [ASVS V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md); [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [Observatory constants.js](https://raw.githubusercontent.com/mdn/mdn-http-observatory/main/src/constants.js)
- **Referrer-Policy.** ASVS 3.4.5 (Level 2): a policy that stops technically sensitive URL data (path and query; hostname as well for internal apps) reaching third parties, via the header or HTML attributes. Observatory runs `referrerPolicyTest`. ZAP’s release table has “Sensitive Information in HTTP Referrer Header” (10025, CWE 598, informational), which is leakage already present in a `Referer` request, not a missing response policy. No release ZAP alert titled Referrer-Policy was in the catalog fetched. User impact: the next site, or its logs, receives the previous URL, including tokens in the query. — [ASVS V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md); [Observatory constants.js](https://raw.githubusercontent.com/mdn/mdn-http-observatory/main/src/constants.js); [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- **CORS allowlist.** ASVS 3.4.2 (Level 1): `Access-Control-Allow-Origin` is a fixed value, or the request `Origin` is checked against an allowlist; `*` must not be used on a response that carries sensitive data. ZAP release 10098 “Cross-Domain Misconfiguration” (CWE 264, medium). Observatory runs `crossOriginResourceSharingTest`. User impact: a hostile origin can read authenticated responses from the victim’s browser. — [ASVS V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md); [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [Observatory constants.js](https://raw.githubusercontent.com/mdn/mdn-http-observatory/main/src/constants.js)
- **Content-Type present.** ZAP release 10019 (CWE 345, informational) for a missing or empty `Content-Type`. ASVS 3.2.1 (Level 1) is the related control: do not let browsers render an API or upload as a document; examples named are `Sec-Fetch-*`, CSP `sandbox`, and `Content-Disposition: attachment`. User impact: a missing type lets the browser sniff the body into an executable context. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [ASVS V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md)
- **Subresource Integrity.** ASVS 3.6.1 (Level 3): third-party static assets need SRI, or a documented exception. ZAP release 90003 “Sub Resource Integrity Attribute Missing” (CWE 345, medium). Observatory runs `subresourceIntegrityTest`. ZAP release 10017 “Cross-Domain JavaScript Source File Inclusion” (CWE 829, low) and 10115 “Script Served From Malicious Domain (polyfill)” (CWE 829, high) are the related passive findings. User impact: a compromised CDN or third-party host can change the script the browser runs. — [ASVS V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md); [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [Observatory constants.js](https://raw.githubusercontent.com/mdn/mdn-http-observatory/main/src/constants.js)
- **Cache directives on sensitive responses.** ZAP release 10015 “Re-examine Cache-control Directives” (CWE 525, informational) and 10050 “Retrieved from Cache” (CWE 525, informational). The richer “Content Cacheability” rule (10049, CWE 524) is beta, not default. User impact: a shared cache or the back button can show someone else’s authenticated page. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- **Charset mismatch.** ZAP release 90011 (CWE 436, informational). User impact: the browser and the server disagree on encoding, which can turn a filter bypass into script. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/)

#### Cookies

Observatory’s cookie test, in the current source, does not look at `__Host-` or `__Secure-` prefixes. It treats a cookie whose name contains `login` or `sess` as a session identifier and one whose name contains `csrf` as an anti-CSRF cookie. It fails a session cookie without `Secure` or without `HttpOnly`, an anti-CSRF cookie without `SameSite`, any cookie without `Secure` (softer result if HSTS passed), `SameSite=None` without `Secure`, and a `SameSite` value other than `lax`, `strict`, or `none`. `heroku-session-affinity` is ignored. No cookies is a pass. — [cookies.js](https://raw.githubusercontent.com/mdn/mdn-http-observatory/main/src/analyzer/tests/cookies.js)

- **Secure attribute.** ASVS 3.3.1 (Level 1): every cookie has `Secure`. ZAP release 10011 (CWE 614, low). User impact: the cookie is sent on a cleartext request and can be stolen on the network. — [ASVS V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md); [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- **HttpOnly on values scripts must not read.** ASVS 3.3.4 (Level 2), with the value also not echoed anywhere except `Set-Cookie`. ZAP release 10010 (CWE 1004, low) flags a missing HttpOnly flag without that “session-like name” heuristic. Observatory only requires HttpOnly on names containing `login` or `sess`. User impact: script running in the origin can read the session token. — [ASVS V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md); [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [cookies.js](https://raw.githubusercontent.com/mdn/mdn-http-observatory/main/src/analyzer/tests/cookies.js)
- **SameSite matched to purpose.** ASVS 3.3.2 (Level 2). ZAP release 10054 (CWE 1275, low): missing, `None`, or invalid. Observatory fails invalid values, `None` without `Secure`, and a missing `SameSite` on an anti-CSRF cookie; a missing `SameSite` on other cookies can still pass under the default expectation. User impact: the browser attaches the cookie to a cross-site request, which is the usual CSRF and some login-CSRF path. — [ASVS V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md); [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [cookies.js](https://raw.githubusercontent.com/mdn/mdn-http-observatory/main/src/analyzer/tests/cookies.js)
- **Cookie scope.** ZAP release 90033 “Loosely Scoped Cookie” (CWE 565, informational). User impact: a sibling host receives a cookie that was meant for one host. This is the problem `__Host-` is designed to close, but it is not the same check. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- **Session identifier in the URL.** ZAP release 3 and 3-3 (CWE 598, medium): session id rewritten into the URL, or leaked in `Referer`. ZAP 10024 (CWE 598, informational) is other sensitive data in the URL. User impact: the session id lands in logs, history, and the next site’s referrer. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- **Oversized cookie.** ASVS 3.3.5 (Level 3): name plus value over 4096 bytes will not be stored. Not a ZAP release rule in the catalog fetched. User impact: the browser drops the cookie and the user loses the function that depended on it. — [ASVS V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md)

#### Information disclosure

ASVS 13.4 says production config should not leak unnecessary data, that these issues are often low on their own, and that they still raise the bar. Debug modes off is 13.4.2 (Level 2). “The application does not expose detailed version information of backend components” is 13.4.6, and it is Level 3, not Level 1. — [ASVS 5.0.0 V13](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x22-V13-Configuration.md)

ZAP release passive rules that match this class:

- Server product in `Server` (10036-1, CWE 497, informational) and version in `Server` (10036-2, CWE 497, low). User impact: the attacker learns which published bugs to try. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- `X-Powered-By` (10037, CWE 497, low), `X-Backend-Server` (10039, CWE 497, low), `X-AspNet-Version` (10061, CWE 933, low), `X-Debug-Token` (10056, CWE 489, low), `X-ChromeLogger-Data` (10052, CWE 532, medium). User impact: framework, internal host, or debug data is handed to every client. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- In-page banners (10009, CWE 497, low), private IP addresses (alert 2, CWE 497, low), suspicious comments (10027, CWE 615, informational), debug error messages (10023, CWE 1295, low), application error disclosure (90022, CWE 550, medium). User impact: stack traces and internal addresses shorten the path to a later bug. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- PII disclosure (10062, CWE 359, high). User impact: personal data is in a response the scanner was allowed to see. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- Hash disclosure (10097, CWE 497): password-hash shapes (NTLM, bcrypt, MD5-crypt, SHA-crypt, LanMan/DES, and similar) are high; bare SHA-1, SHA-256, MD5, and similar digests are low. User impact: a stolen password hash can be attacked offline. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- Tech-from-version with known vulnerabilities, release passive 20020 (CWE 1395): PHP and Apache HTTP Server version strings, high when the version is known-vulnerable and low when it is only possibly vulnerable. The passive scanner rules changelog of 14 Apr 2026 says rules gained OWASP Top 10 2025 tags. User impact: the banner names a build that already has a public bug. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [pscanrules changelog](https://www.zaproxy.org/docs/addons/pscanrules/changelog/)
- Vulnerable JS library (10003, CWE 1395, medium, release passive). User impact: the page loads a script version with a known client-side bug. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- Timestamp disclosure (10096, CWE 497, low) and username-hash found (10057, CWE 284, informational) are release passive but noisy. User impact is usually low unless the value is actually a secret. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/)

WSTG-INFO-03 still tells testers to read `robots.txt` (RFC 9309), robots meta tags, sitemaps, `humans.txt`, and other `.well-known` URIs. It says `Disallow` is not an access control, and that AI-crawler `User-agent` blocks (the page names `GPTBot` and `ClaudeBot` as examples) may be ignored, so a sensitive path listed there is still discoverable. The chapter’s own sample was taken 13 Sep 2026. User impact: the file is a map of paths the operator hoped crawlers would skip. — [WSTG-INFO-03](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/01-Information_Gathering/03-Review_Webserver_Metafiles_for_Information_Leakage/)

#### Exposed files and listings

- **Directory listing.** ASVS 13.4.3 (Level 2): no listings unless intended. ZAP release passive 10033 “Directory Browsing” (CWE 548, medium). There is also an active rule, alert 0, same CWE. User impact: the browser is given a file index the application never linked. — [ASVS V13](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x22-V13-Configuration.md); [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- **Source-control metadata.** ASVS 13.4.1 (Level 1): no accessible `.git` or `.svn`, including to the application itself. ZAP’s “Source Code Disclosure - Git/SVN” rules (41, 42) are beta and active, not default passive. User impact: the repository history, which often contains secrets, is downloadable. — [ASVS V13](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x22-V13-Configuration.md); [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- **Debug, docs, and monitoring endpoints.** ASVS 13.4.2 and 13.4.5 (Level 2). ZAP’s passive recon alerts for admin paths, debug paths, Spring Boot actuators, Swagger, GraphQL, backup files, env files, `.git`, and phpinfo are ids under 200019 and are typed Tool, status beta, not release passive. User impact: an operator console or config file is reachable without the review that would have put it behind authentication. — [ASVS V13](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x22-V13-Configuration.md); [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- **File-extension allowlist.** ASVS 13.4.7 (Level 3). WSTG’s configuration index still lists file-extension handling and backup-file review. ZAP “Backup File Disclosure” (10095, CWE 530) is beta and active. User impact: a backup or source file is served next to the page. — [ASVS V13](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x22-V13-Configuration.md); [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- **TRACE.** ASVS 13.4.4 (Level 2): TRACE not supported in production. ZAP’s insecure-method checks, including TRACE, are beta and active (90028). User impact: TRACE can echo request headers, which has historically leaked cookies on some stacks. — [ASVS V13](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x22-V13-Configuration.md); [ZAP alert details](https://www.zaproxy.org/docs/alerts/)

#### TLS certificate

- **Publicly trusted certificate on external HTTP services.** ASVS 12.2.2 (Level 1). User impact: the user, or their software, must accept an untrusted issuer, which is the same prompt a network attacker needs. — [ASVS V12](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x21-V12-Secure-Communication.md)
- **Clients validate the certificate they receive.** ASVS 12.3.2 (Level 2), aimed at service-to-service clients. User impact: a mis-issued or intercepted certificate is accepted. — [ASVS V12](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x21-V12-Secure-Communication.md)
- **Revocation via OCSP stapling.** ASVS 12.1.4 (Level 3). User impact: a revoked certificate keeps working until it expires. — [ASVS V12](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x21-V12-Secure-Communication.md)
- **Separate certificates per environment.** ASVS V12’s narrative says a wildcard used across production and non-production is not inherently insecure, but compromise of that one certificate widens the blast radius. It is guidance, not a numbered fail. — [ASVS V12](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x21-V12-Secure-Communication.md)
- **Heartbleed, indicative.** ZAP release passive 10034 (CWE 119, high) is labeled “Indicative,” not a live handshake probe. User impact: if the evidence is real, a network attacker can read process memory, including keys. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- MDN HTTP Observatory does not report certificate or TLS details. — [MDN Observatory launch](https://developer.mozilla.org/en-US/blog/mdn-http-observatory-launch/)

#### DNS

- No CAA, DNSSEC, SPF, DKIM, or DMARC check appears in the ZAP release passive catalog fetched, in Observatory’s twelve tests, or in ASVS V3, V12, or V13. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [Observatory constants.js](https://raw.githubusercontent.com/mdn/mdn-http-observatory/main/src/constants.js); [ASVS V12](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x21-V12-Secure-Communication.md); [ASVS V13](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x22-V13-Configuration.md)
- The WSTG configuration index still lists “Test for Subdomain Takeover” (the indexed outline calls it 4.2.10). That is a DNS-dangling check, and it is not decidable from one HTTP response. The chapter body was not fetched. — [WSTG configuration index as indexed](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/02-Configuration_and_Deployment_Management_Testing/README)
- `security.txt` may point at an `OPENPGPKEY` DNS name in the Encryption field. That is an optional contact mechanism, not a DNSSEC finding. — [RFC 9116 §2.5.4](https://www.rfc-editor.org/rfc/rfc9116.html)

### Inferences

- A default passive profile that matches all three of ZAP release, Observatory, and ASVS Level 1 is smaller than the union. The intersection is: HTTPS with no mixed content or insecure form target, HSTS with a long `max-age`, CSP present, framing control present, `nosniff`, Referrer-Policy, CORS not wide open on sensitive responses, and `Secure` on cookies. HttpOnly and SameSite are Level 2 in ASVS but already default ZAP and, for session-like names, Observatory.
- ASVS Level 3 items (CSP reporting, HSTS preload, SRI, OCSP stapling, ECH, cookie size, COOP) should be reported as hardening, not as the same severity as a missing Level 1 control.
- Version banners are still worth reporting, but ASVS only requires hiding detailed backend versions at Level 3. A scanner that fails a build for `Server: nginx` with no version is stricter than ASVS 5.0.0 Level 1.

### Gaps

- The current Observatory score modifiers (how many points a missing CSP or a short HSTS `max-age` costs, and whether COOP/COEP are pass/fail or bonus) were not read. `constants.js` only proves the tests exist.
- WSTG chapter bodies for HSTS, CSP, and “other HTTP security header misconfigurations” were not retrieved; the live slugs tried returned 404. Only the indexed chapter list and WSTG-INFO-03 were confirmed by fetch.
- ASVS appendix C (cryptography standards) was not opened, so this note does not claim what it says about specific cipher names or post-quantum algorithms.
- No baseline DNS-email or CAA catalog was found in these four sources.

## What new or newly emphasized checks showed up in 2025–2026?

### Takeaway

The checks these primary sources newly require or newly score, as opposed to long-standing header hygiene, are cookie name prefixes in ASVS 5.0.0, COOP at ASVS Level 3, CORP and COEP/COOP inside current Observatory and as ZAP beta rules, `security.txt` as a WSTG information-gathering item, and TLS 1.2/1.3 only. Permissions-Policy is a ZAP beta rule and is not an ASVS 5.0.0 requirement. No primary source reviewed here says a default web scan must fail a site that lacks post-quantum hybrid TLS; WSTG and the OWASP Quantum Security Project do say testers and operators should look at the negotiated group.

### Cited Findings

- **Cookie prefixes `__Secure-` and `__Host-`.** ASVS 5.0.0, released May 2025: 3.3.1 (Level 1) requires `Secure` and, if the name does not use `__Host-`, it must use `__Secure-`. 3.3.3 (Level 2) requires `__Host-` unless the cookie is explicitly shared with other hosts. The normative references point at MDN’s cookie-prefix section. ZAP’s release cookie rules fetched on 12 Nov 2026 do not include a prefix alert. Observatory’s `cookies.js` does not check prefixes. User impact: without the prefix, script or a different host at the same site can overwrite the cookie. — [ASVS V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md); [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [cookies.js](https://raw.githubusercontent.com/mdn/mdn-http-observatory/main/src/analyzer/tests/cookies.js)
- **`__Host-Http-` / `__Http-` are not required yet.** An ASVS issue opened 12 Feb 2026 asks whether 3.3.4 should also require the newer `__Host-Http-` prefix so script cannot overwrite an HttpOnly cookie. The issue states that 5.0.0 already requires `__Host-` (3.3.3) and HttpOnly where script must not read the value (3.3.4). It does not change the published standard. The issue’s browser-coverage figure is the author’s caniuse citation, not an ASVS requirement. — [OWASP/ASVS issue 3331](https://github.com/OWASP/ASVS/issues/3331)
- **COOP.** ASVS 3.4.8 (Level 3): document responses (`Content-Type: text/html`) send `Cross-Origin-Opener-Policy: same-origin` or `same-origin-allow-popups`, to stop tabnabbing and frame counting via a shared window. Observatory’s version-6 list includes `crossOriginOpenerPolicyTest`. ZAP 90004-3 “Cross-Origin-Opener-Policy Header Missing or Invalid” is beta, low, CWE 693, under “Insufficient Site Isolation Against Spectre Vulnerability.” A separate beta tool alert 200005-23 flags COOP that is not `same-origin`, and 200005-13 flags COOP set without COEP/CORP. The July 2024 Observatory launch post’s narrative test list names CORP but not COOP; the current source file includes COOP. User impact: a cross-origin page that opened this one can still reach its window. — [ASVS V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md); [Observatory constants.js](https://raw.githubusercontent.com/mdn/mdn-http-observatory/main/src/constants.js); [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [MDN Observatory launch](https://developer.mozilla.org/en-US/blog/mdn-http-observatory-launch/)
- **COEP.** Not a numbered ASVS 5.0.0 V3 requirement. Observatory version 6 includes `crossOriginEmbedderPolicyTest`. ZAP 90004-2 is beta, low, CWE 693. Beta tool alert 200005-14 flags a COEP value other than `require-corp` or `credentialless`. User impact: without COEP, the page cannot claim cross-origin isolation, and a Spectre-style leak from a cross-origin resource is easier. — [Observatory constants.js](https://raw.githubusercontent.com/mdn/mdn-http-observatory/main/src/constants.js); [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [ASVS V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md)
- **CORP.** ASVS 3.5.8 (Level 3) allows a restrictive `Cross-Origin-Resource-Policy` as one way to stop authenticated resources being embedded cross-origin; validating `Sec-Fetch-*` is the alternative. Observatory added CORP at the 2024 migration and still runs `crossOriginResourcePolicyTest`. ZAP 90004-1 is beta, low, CWE 693. User impact: another origin can load a credentialed resource and measure it. — [ASVS V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md); [MDN Observatory launch](https://developer.mozilla.org/en-US/blog/mdn-http-observatory-launch/); [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- **Permissions-Policy.** ZAP 10063 “Permissions Policy Header Not Set” is beta, low, CWE 693, and 10063-2 flags a deprecated `Feature-Policy` (CWE 16). Beta tool alert 200005-15 flags deprecated Feature-Policy or an unknown or overly permissive Permissions-Policy. ASVS 5.0.0 V3.4 does not require the header. Observatory’s twelve tests do not include it. User impact: the page can use powerful browser features (camera, microphone, and similar) that a locked-down policy would have refused. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [ASVS V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md); [Observatory constants.js](https://raw.githubusercontent.com/mdn/mdn-http-observatory/main/src/constants.js)
- **Browsing Topics.** No ZAP alert, Observatory test, or ASVS 5.0.0 requirement reviewed here names the Browsing Topics API or a `browsing-topics` Permissions-Policy token as its own check.
- **security.txt.** RFC 9116 (April 2022, Informational) is the format. For web services the file must be at `/.well-known/security.txt`, fetched with HTTPS, `Content-Type: text/plain` (UTF-8). A copy at `/security.txt` is legacy; if both exist, the `.well-known` copy must be used. The file applies only to the host that served it, not to parent or child names. `Contact` must appear and is a URI (`mailto:`, `https:`, or `tel:`). `Expires` must appear exactly once; after that instant the file is stale and should not be used. The RFC recommends `Expires` less than a year ahead. If `Canonical` is present and the retrieval URL is not listed, the file should not be trusted. Web URIs in the defined fields must be `https`. WSTG-INFO-03, in the “latest” guide fetched 12 Nov 2026, tells testers to retrieve both locations and treats the file as a source of further paths, disclosure-policy links, and bug-bounty information, citing securitytxt.org and RFC 9116. ZAP alert 200013-1 “security.txt observed” is beta, informational, type Tool, CWE 200. That is “we saw the file,” not “the file is missing or expired.” User impact of a missing or stale file: a researcher has no reliable contact, so a vulnerability is more likely to be disclosed in public or not reported at all. A file on a compromised host can also redirect reports to an attacker; the RFC’s own mitigation is `Canonical` plus an OpenPGP signature, which a scanner can note but not fully prove. — [RFC 9116](https://www.rfc-editor.org/rfc/rfc9116.html); [WSTG-INFO-03](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/01-Information_Gathering/03-Review_Webserver_Metafiles_for_Information_Leakage/); [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- **TLS 1.0 and 1.1 off.** ASVS 12.1.1 (Level 1) names TLS 1.2 and TLS 1.3 as the examples of “latest recommended versions” and says the latest must be preferred. It does not list 1.0 or 1.1. This is the requirement to implement, not a new 2026 RFC. User impact: those protocols have known weaknesses and exist only so an attacker can negotiate them. — [ASVS V12](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x21-V12-Secure-Communication.md)
- **Encrypted Client Hello.** ASVS 12.1.5 (Level 3): ECH enabled so SNI is not exposed in the handshake. User impact: a path observer learns the hostname the client asked for. This is not visible in HTTP response headers. — [ASVS V12](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x21-V12-Secure-Communication.md)
- **Post-quantum or hybrid TLS.** ASVS 12.1.1 does not mention hybrid or ML-KEM. MDN Observatory does not inspect TLS. The ZAP alert table fetched has no post-quantum rule. The OWASP WSTG weak-transport page, as returned by search indexing of `https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/09-Testing_for_Weak_Cryptography/01-Testing_for_Weak_Transport_Layer_Security` (tool timestamp 30 Jun 2026), says TLS 1.3 should be preferred over TLS 1.2 because of post-quantum cipher compatibility, that signature and key exchange should support post-quantum cryptography, that hybrid constructions such as X25519+ML-KEM-768 may be used during the transition, and that automated TLS testers include Nmap, O-Saft, sslscan, sslyze, SSL Labs, and testssl.sh. A direct fetch of the matching `wstg.owasp.org` slug on 12 Nov 2026 returned 404, so this paragraph is index evidence, not a re-fetched chapter. OWASP Quantum Top 10 QS01:2026 says to migrate channels that need it to hybrid post-quantum TLS using ML-KEM. QS06:2026 says to monitor the negotiated group in production and alert on classical-only handshakes, and it names RFC 9954 (July 2026) as the hybrid construction. That is operator monitoring, not a ZAP or Observatory passive rule. Vendor adoption write-ups (GeoTrust’s October 2026 crawl, DigiCert’s August 2026 migration note) describe how common hybrid key exchange has become; they are not scanner-policy pages and are not used here as a “must fail” rule. — [ASVS V12](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x21-V12-Secure-Communication.md); [Observatory launch](https://developer.mozilla.org/en-US/blog/mdn-http-observatory-launch/); [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [WSTG weak TLS, search index](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/09-Testing_for_Weak_Cryptography/01-Testing_for_Weak_Transport_Layer_Security); [QS01](https://raw.githubusercontent.com/OWASP/quantum-security-project/Top10/quantum-top-10/QS01_Harvest-Now-Decrypt-Later-Exposure.md); [QS06](https://github.com/OWASP/quantum-security-project/blob/main/quantum-top-10/QS06_Insecure-Migration-and-Hybrid-Misuse.md)
- **Fetch metadata on the request.** ZAP 90005 (`Sec-Fetch-Site`, `Sec-Fetch-Mode`, `Sec-Fetch-Dest`, `Sec-Fetch-User` missing or invalid) is alpha and informational (CWE 352). ASVS 3.5.3 and 3.5.8 (Level 1 and Level 3) name `Sec-Fetch-*` as a server-side check the application should perform, which a scanner cannot prove by seeing the request header alone. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/); [ASVS V3](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md)
- **CSP “Header & Meta” alert withdrawn in code, still listed.** Passive scanner rules changelog 76 (25 Sep 2026) says alert 10055-12 is no longer raised. The public alert table fetched 12 Nov 2026 still lists 10055-12 as release, informational, CWE 693. Do not treat the table row as proof the alert still fires. — [pscanrules changelog](https://www.zaproxy.org/docs/addons/pscanrules/changelog/); [ZAP alert details](https://www.zaproxy.org/docs/alerts/)

### Inferences

- For a 2026 default passive profile, add `__Secure-` / `__Host-` because ASVS Level 1 now requires a prefix, and add a non-destructive `security.txt` fetch because WSTG-INFO-03 treats it as routine information gathering. Report COOP/COEP/CORP and Permissions-Policy as informational or beta-equivalent unless the program is aiming at ASVS Level 3, where COOP and CORP are actually required.
- Do not fail a default scan for lack of X25519MLKEM768. Surface it only as an optional TLS observation if the scanner already speaks TLS, and label it as transition guidance (WSTG index text and QS06), not as a missing Level 1 control.
- Do not add a Browsing Topics check until a primary scanner or ASVS requirement names it. A Permissions-Policy parser can record the token if the header is already being read, but that would be product invention, not a sourced baseline.

### Gaps

- Observatory’s current COOP, COEP, and CORP score modifiers were not read, so it is not confirmed whether a missing COOP fails the grade or only loses a bonus.
- The WSTG weak-TLS chapter could not be re-fetched from `wstg.owasp.org` on 12 Nov 2026. The post-quantum sentences depend on the search index of the older OWASP URL.
- No primary page was found that tells a scanner to report the Browsing Topics API specifically.
- ASVS appendix C was not read, so a post-quantum requirement hiding there would have been missed.

## Which of those checks can be decided from response headers and a single page fetch, with no attack payload?

### Takeaway

Almost every header, cookie, and in-page disclosure check above is decided from one response: status, headers, and the HTML body. TLS version, certificate trust, HSTS preload, the HTTP-to-HTTPS first hop, `security.txt`, source-control directories, and DNS are not. None of the decidable checks need an attack payload; the ones that need a second URL still only need an ordinary GET.

### Cited Findings

- ZAP defines passive scanning as examining traffic that was already proxied, and says proxying and passive scanning do not themselves attack the application. — [ZAP scanning FAQ](https://www.zaproxy.org/faq/is-there-any-danger-when-scanning-with-zap-against-a-live-website-e-g-create-delete-update-corrupt-data/)
- Observatory’s documented method is to request the site and judge headers, cookies, redirects, SRI, and CORS. The launch post says the redirection test specifically requests the plain HTTP URL and checks the first hop. SRI and mixed-content checks need the document body, not only headers. — [MDN Observatory launch](https://developer.mozilla.org/en-US/blog/mdn-http-observatory-launch/)
- RFC 9116 places `security.txt` at a different path from the home page, and requires HTTPS. That is a second ordinary GET, not a payload. — [RFC 9116 §3](https://www.rfc-editor.org/rfc/rfc9116.html)
- ASVS 12.1 and 12.2 are properties of the handshake and the certificate, which a header dump does not contain. Observatory documents that it does not collect them. — [ASVS V12](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x21-V12-Secure-Communication.md); [MDN Observatory launch](https://developer.mozilla.org/en-US/blog/mdn-http-observatory-launch/)
- WSTG-INFO-03 retrieves `robots.txt`, sitemaps, `humans.txt`, and `security.txt` as separate URLs. — [WSTG-INFO-03](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/01-Information_Gathering/03-Review_Webserver_Metafiles_for_Information_Leakage/)

### Inferences

Decidable from the headers of one response, no payload:

- HSTS presence, `max-age`, `includeSubDomains`, duplicates, and “HSTS on HTTP.”
- CSP presence and the policy text (wildcards, `unsafe-inline`, `unsafe-eval`, `object-src`, `base-uri`, `frame-ancestors`).
- `X-Frame-Options` presence and syntax, with the ASVS caveat that it is obsolete beside `frame-ancestors`.
- `X-Content-Type-Options: nosniff`.
- `Referrer-Policy`.
- `Access-Control-Allow-Origin` and `Access-Control-Allow-Credentials` on that response. Whether the value is a reflection of an attacker `Origin` cannot be decided without a second request that sets `Origin`. Report a reflected or `*` value as a lead, not as a confirmed credentialed read.
- COOP, COEP, CORP, and Permissions-Policy / Feature-Policy on that response.
- `Content-Type` missing or empty, and charset agreement between `Content-Type` and the body.
- `Set-Cookie` flags: `Secure`, `HttpOnly`, `SameSite`, `__Host-` / `__Secure-` prefix, `Domain` scope, and name-plus-value length. A cookie set only on another path will not be seen.
- Disclosure headers: `Server`, `X-Powered-By`, `X-AspNet-Version`, `X-Backend-Server`, `X-Debug-Token`, `X-ChromeLogger-Data`.
- Cache-Control / Pragma on that response.

Decidable from the body of that same response, still no payload:

- CSP in a meta element, mixed content URLs, form actions that change scheme, cross-origin scripts, missing SRI on those scripts, the polyfill-domain script check, robots meta, suspicious comments, stack traces, private IPs, PII and hash patterns, vulnerable JS library names, and a directory listing if the URL fetched is the listing.

Not decidable from one page response:

- First-hop HTTP to HTTPS redirect, and HSTS preload-list membership (needs the preload list, which ASVS 3.7.4 treats as a separate control).
- TLS version, cipher suite, forward secrecy, certificate public trust, expiry, hostname match, OCSP stapling, ECH, and hybrid post-quantum group. These need a handshake. Heartbleed-indicative evidence is only in scope if the bytes are already in the captured stream.
- `security.txt` existence, staleness, and `Canonical` match. Needs `GET /.well-known/security.txt` and, if reporting legacy behavior, `GET /security.txt`.
- `robots.txt`, sitemap, `humans.txt`.
- `.git`, `.svn`, backup files, admin panels, and actuators, unless that exact URL was the one page fetched. Confirming they are exposed means requesting those paths. ASVS wants them inaccessible; requesting a well-known path with GET is discovery, not an exploit payload, but it is not “the page the user already fetched.”
- Subdomain takeover and any DNS record.
- Whether the application actually enforces `Sec-Fetch-*` or an allowlist. Seeing the request header does not prove the server checked it.

### Gaps

- It was not confirmed from Observatory source whether the version-6 grade still consults the HSTS preload list. ASVS Level 3 requires preload; the launch post describes the redirect test but the preload check was not re-read in the current test file.
- “Single page” will miss cookies and headers that differ on the login response. The sources do not say one URL is complete coverage.

## What should stay out of a default scan?

### Takeaway

ZAP, Nuclei, and PortSwigger all separate a non-destructive look at normal traffic from checks that send extra or hostile requests. Default or explicitly “safe” profiles exclude denial-of-service and fuzz templates (Nuclei), intrusive audit checks (Burp, when that configuration is selected), and active scan rules that can create, change, or delete data (ZAP). None of the three policy pages reviewed uses the phrase “credential stuffing.” Authorization is required before any scan that goes beyond looking at your own traffic.

### Cited Findings

- **ZAP.** “Proxying (and therefore passive scanning) requests via ZAP is completely safe and legal, it just allows you to see whats going on.” Spidering “could cause problems depending on how your application works,” and an option exists to avoid POST during the spider, which is safer and less effective. “Active scanning is dangerous and depending on your app may create/modify/delete data.” Passive scanning is “the only really safe thing”; spidering and active scanning “could be considered illegal if you perform them on apps you don’t have permission to test.” Safe mode allows only safe operations. Protected mode limits attack actions to sites the user marked in scope. The project recommends one of those two modes “whenever you are using ZAP with a site that you do not want to attack.” — [ZAP scanning FAQ](https://www.zaproxy.org/faq/is-there-any-danger-when-scanning-with-zap-against-a-live-website-e-g-create-delete-update-corrupt-data/)
- **ZAP default rule status.** Only release rules are in the product by default. The active rules for path traversal, remote file inclusion, command injection, SQL injection, XXE, and similar are therefore not part of a passive run. The old Apache Range header denial-of-service rule (10053) is deprecated. — [ZAP alert details](https://www.zaproxy.org/docs/alerts/)
- **Nuclei, default template exclusion.** The project FAQ says safety is both “the traffic Nuclei creates” and “the impact templates have on the target.” The template library includes templates “which perform fuzzing and other actions which may result in a DoS against the target system.” Those are tagged and “excluded from the default scan” and run only when the user passes `-itags`. A default run of the full template set is described as several thousand requests and “over 3500 templates.” The linked ignore file lists tags `fuzz` and `dos`, and also drops named template files “because they have weak matchers and may generate FP results.” The FAQ also says to validate a result a second time before reporting it. — [Nuclei FAQ](https://docs.projectdiscovery.io/opensource/nuclei/faq); [.nuclei-ignore](https://github.com/projectdiscovery/nuclei-templates/blob/master/.nuclei-ignore)
- **ProjectDiscovery terms (24 Sep 2026 in the search index).** The services may be used “only on systems and Assets that you own or that you have explicit, written authorization to test,” including a bug-bounty scope that covers the test. The customer warrants that authorization and must be able to show it. Unauthorized testing “may violate laws such as the U.S. Computer Fraud and Abuse Act and the UK Computer Misuse Act.” Section 4.3 prohibits scanning or attacking a system without that authorization, and prohibits use “for unauthorized surveillance, stalking, or tracking.” The terms also say scans and AI features “can slow, disrupt, or change the systems they target,” and the customer is responsible for that effect. The terms page was not re-fetched in full; this is the search-index text of `https://projectdiscovery.io/terms`. — [ProjectDiscovery Terms of Service](https://projectdiscovery.io/terms)
- **PortSwigger, product warning.** Burp’s documentation home, updated 6 Nov 2026, says Burp “contains functionality that can damage target systems,” that testing “inherently involves interacting with targets in non-standard ways that can cause problems,” and that the user should not use Burp on systems they are not authorized to test or where the owner has not accepted the risk of damage. — [Burp Suite documentation](https://portswigger.net/burp/documentation)
- **PortSwigger, intrusive and time-based checks.** The auditing chapter, updated 6 Nov 2026, says medium-active checks “send modified requests that the application might interpret as malicious” and “may trigger security alerts, log users out, or cause other unintended effects.” Intrusive-active checks “simulate real-world attacks and carry a significant risk of modifying or damaging the application or its data,” and “may cause permanent data loss, service outages, or other irreversible impacts.” The built-in configuration “Audit checks - passive” selects only issues “detected by auditing normal requests and responses” and “should not affect the running of the web application.” “Audit checks - light active” disables medium and intrusive checks and “significantly reduces the risk of damage or data loss.” “Audit checks - medium active” disables intrusive checks and still notes that medium and light checks “may still impact how the web application runs.” “Audit checks - all except time-based detection methods” exists because those methods include “intentionally causing page time-outs and making database sleep calls.” These are selectable configurations. The page does not say the unnamed factory default already excludes intrusive checks. — [Auditing](https://portswigger.net/burp/documentation/scanner/auditing); [Built-in configurations](https://portswigger.net/burp/documentation/scanner/scan-configurations/burp-scanner-built-in-configs)
- **PortSwigger’s own bounty is a different document.** It forbids denial-of-service attacks, unthrottled automated scanning (throttle to one request per second), and says they are not interested in missing rate limits or denial-of-service vulnerabilities. That is the program’s scope for people testing PortSwigger, not the default configuration of Burp Scanner. It is cited only so the two are not confused. — [PortSwigger on HackerOne](https://hackerone.com/portswigger)
- **What “passive” means for Burp.** Passive issues “can be detected by examining the application’s normal requests and responses.” Light-active issues “require only a small number of benign additional requests.” — [Built-in configurations](https://portswigger.net/burp/documentation/scanner/scan-configurations/burp-scanner-built-in-configs)

### Inferences

- A default scan for this product should stay inside ZAP’s “passive” and Burp’s “Audit checks - passive” description: decisions from responses the crawl or the user already received, plus ordinary GETs of well-known disclosure files (`robots.txt`, `security.txt`). That matches every check in the previous section that was marked decidable without a payload.
- Keep out of that default, because the vendors say so: fuzzing templates, templates tagged for denial of service, time-based sleep and forced timeouts, intrusive confirmation that writes or deletes data, and any active injection, SSRF, or authentication-bypass payload. Those belong behind an explicit opt-in, the way Nuclei requires `-itags` and the way ZAP separates active scan from passive scan.
- Spidering is not free. ZAP says it can be dangerous, especially if it submits POST requests. A default “single page plus headers” mode should not crawl state-changing actions.
- Credential stuffing is not named. The closest sourced rules are “do not send attacks without authorization” and “active checks can modify data.” A login-guessing or password-list module would fall on the prohibited side of those rules even though the word “stuffing” is absent. Do not add one to a default scan.

### Gaps

- No ZAP, Nuclei, or PortSwigger policy page found in this pass uses the words “credential stuffing” or “password spraying.” The exclusion is inferred from the active-scan and authorization rules, not from a sentence that names those attacks.
- PortSwigger documents configurations that turn intrusive checks off. It does not, on the page fetched, state which audit classes are enabled in an unmodified new scan. Do not write “Burp’s default excludes intrusive checks” without a clearer citation.
- The ProjectDiscovery terms were taken from the search index of 24 Sep 2026, not a full re-fetch. Section numbers 4.1 and 4.3 match that index. If the page has moved since, the quotes need a re-read.
