# Scanner throughput without overwhelming the target

Research date: 12 November 2026. Scope is published concurrency, rate-limit, timeout, retry, pool, body-cap, and politeness behavior for a Rust HTTP scanner that already uses reqwest, a shared rate limit, a bound on in-flight requests, and a cap on how much of a response body is analyzed. No exploit payloads, evasion, or WAF-bypass material is included.

Unverified aggregator pages (apis.io “Owasp Zap Rate Limits” and “Nuclei API Rate Limits”, dated 2026 and labeled generated/unverified, and a Cyberly how-to that invents ZAP defaults) were discarded. Numbers below appear only when a primary doc, RFC, or project source states them.

## What concurrency, rate-limit, timeout, retry, and pool settings do published scanners document?

### Takeaway

ZAP, Nuclei, and Burp all separate a concurrency cap from a send-rate or inter-request delay, and none of them publish one universal “safe RPS.” Nuclei is the only one of the three that ships numeric defaults for both parallelism and a global requests-per-second cap (25/25 and 150/s). ZAP and Burp expose the knobs and document qualitative strain, but the operator chooses the rate.

### Cited Findings

- ZAP’s Network Rate Limit applies to HTTP/HTTPS, not WebSockets, and exists “to prevent overloading the target or being blocked.” A host that matches several rules uses “the rule with the most restrictive rate.” Each rule has a “Requests Per Second” maximum. Group By default is “rule,” which limits every host matching that rule as one unit; “host” applies the same RPS to each host separately. The docs do not publish a default rule or a default RPS. — [ZAP Rate Limit](https://www.zaproxy.org/docs/desktop/addons/network/options/ratelimit/)
- ZAP active scan has two concurrency knobs with no numeric defaults on the options page: “Number of Hosts Scanned Concurrently” and “Concurrent Scanning Threads per Host.” Raising threads “will speed up the scan but may put extra strain on the computer ZAP is running on and the target host.” — [ZAP Options Active Scan](https://www.zaproxy.org/docs/desktop/ui/dialogs/options/ascan/)
- In ZAP 2.17.0 source, the fallback for hosts scanned at once is 2 (`getInt(HOST_PER_SCAN, 2)`), and threads per host fall back to `Constant.getDefaultThreadCount()` with a floor of 1. — [ScannerParam.java (zaproxy 2.17.0)](https://fossies.org/dox/zaproxy-2.17.0/ScannerParam_8java_source.html)
- A ZAP maintainer issue (milestone 2.13.0, closed) changed scanner, spider, fuzzer, forced-browse, and related tools so the default thread count is the number of available processors (`Runtime.getRuntime().availableProcessors()`), because “increasing the number of threads makes a significant performance improvement.” The issue does not print a single integer default. — [zaproxy#7663](https://github.com/zaproxy/zaproxy/issues/7663)
- ZAP’s “Delay When Scanning (In Milliseconds)” is deprecated. A non-zero delay “will put less of a strain on the target host,” but the docs say to use Network Rate Limit instead, because rate limit “allows to enforce the rate at which the requests are sent while the Delay When Scanning doesn’t.” — [ZAP Options Active Scan](https://www.zaproxy.org/docs/desktop/ui/dialogs/options/ascan/)
- ZAP connection and read timeout default is 20 seconds. “A higher timeout allows to test slower applications.” DNS TTL for successful queries defaults to 30 seconds. “Use Global HTTP State” defaults to unselected; when selected, “session tracking ensures that any requests are sent with the latest session details.” — [ZAP Connection options](https://www.zaproxy.org/docs/desktop/addons/network/options/connection/)
- ZAP’s speed FAQ says a significant part of scan time is network requests, so more threads and browsers speed scans while waiting on responses, but “using too many threads / browsers may cause problems with either the computer running ZAP or the target app.” It does not give a recommended thread count. — [How can you speed up scans?](https://www.zaproxy.org/faq/how-can-you-speed-up-scans/)
- Nuclei `-c` / `-concurrency` defaults to 25. In template-spray (the default; `auto` is “currently a placeholder for template-spray”) it is how many templates run at once, and it is also the per-template request concurrency when a template does not set `threads`. In host-spray it is templates in parallel per target. `-bs` / `-bulk-size` defaults to 25: targets in parallel per template (template-spray) or targets in parallel at a time (host-spray). — [Mass Scanning with Nuclei](https://docs.projectdiscovery.io/opensource/nuclei/mass-scanning-cli)
- Nuclei `-rl` / `-rate-limit` defaults to 150 HTTP requests per second, global. The same page says a low rate “directly affects speed (RPS) and Memory Usage” because “ratelimit is applied just before sending requests but at this point the requests are already prepared and are in memory waiting to be sent.” `-rlm` (requests per minute) is an alternative and “mutually exclusive with `-rl`.” `-timeout` default is 10 seconds for HTTP (code protocol uses `6 *` that value). `-retries` default is 1. `-mhe` / `-max-host-error` default is 30 network errors per host before the host is removed. Disabling that (`-nmhe`) “keeps unresponsive hosts in memory and retries them.” — [Mass Scanning with Nuclei](https://docs.projectdiscovery.io/opensource/nuclei/mass-scanning-cli)
- Nuclei dev CLI source sets `-rate-limit-duration` / `-rld` default to `time.Second`, `-headless-bulk-size` 10, `-headless-concurrency` 10, `-js-concurrency` 120, `-payload-concurrency` 25, alongside the 150 / 25 / 25 / timeout 10 / retries 1 defaults above. — [nuclei `cmd/nuclei/main.go` (dev)](https://raw.githubusercontent.com/projectdiscovery/nuclei/dev/cmd/nuclei/main.go)
- Nuclei headless variants of bulk size and concurrency exist “since headless templates are resource intensive.” JavaScript runtime concurrency defaults to 120 and “is tested to be optimal with minimal resource utilization”; runtimes are reused. Payload concurrency (`-pc`, default 25, added in v3.2.0) applies only when a template has `payloads` and does not set `threads`. — [Mass Scanning with Nuclei](https://docs.projectdiscovery.io/opensource/nuclei/mass-scanning-cli)
- Nuclei template-spray “does not aggressively scan a single target” and is described as the stealthier strategy; it “consumes more memory than host-spray” because each template gets its own copy of the target chunk. Host-spray runs all templates on one target before the next. “There is no out-of-the-box solution to optimize Nuclei automatically”; the docs say to adjust `-c`, `-bs`, and `-rl` to the scanner host and the targets, prefer host-spray when possible, and batch targets. — [Mass Scanning with Nuclei](https://docs.projectdiscovery.io/opensource/nuclei/mass-scanning-cli)
- Burp Scanner and Burp Intruder share project-level resource pools. A pool can set “Maximum concurrent requests” (simultaneous sends, “so you don't overload the server”) and “Delay between requests” in milliseconds, as Fixed, “With random variations,” or “Increase delay in increments.” No numeric default for either control is stated. Automatic throttling, on by response code, “adds a short delay between requests” for 429, 503, or other codes the user lists. PortSwigger says to throttle error codes only: throttling on `200 (OK)` “could result in significantly decreased scan performance.” — [Burp Tasks settings](https://portswigger.net/burp/documentation/desktop/settings/project/tasks)
- Resource pools “are not available for passive crawl tasks.” If no pool is selected, the scan uses the default resource pool. Pools can be reassigned while a task runs. — [Managing resource pools for scans](https://portswigger.net/burp/documentation/desktop/running-scans/managing-resource-pools)
- Burp’s task-execution text describes pools as controlling “the number of requests that can be made concurrently, or the rate at which requests can be made, or both,” and gives an operator pattern: a full crawl-and-audit in the background “with a small number of concurrent requests,” and a selected-request audit “with a larger number of concurrent requests to give it priority.” No integers are given. — [Task execution settings](https://portswigger.net/burp/documentation/desktop/running-scans/live-tasks/task-execution-settings)
- Burp Suite DAST custom scan config: “Enable concurrent request limiting,” “Throttle request interval” in milliseconds, and “Add random variations to interval,” which “randomly adding or removing up to 50%” of the interval (stated example: 500 ms varies between 250 and 750). “Auto backoff” “automatically adds a short delay” and “incrementally increases until the request limit complies with the server's rate limit.” “Default to HTTP/2 if the server supports it” is a separate connection option. — [Custom scan configuration settings](https://portswigger.net/burp/documentation/dast/user-guide/reference/custom-scan-config-settings)
- Burp Suite DAST’s per-machine “Concurrent scan limit” defaults to 1 for a newly added scanning machine. That is a cap on scans, not on HTTP requests inside a scan. The docs say to raise it slowly if the machine has enough RAM and CPU. — [Assigning scan limits](https://portswigger.net/burp/documentation/dast/user-guide/managing-scanning-resources/assigning-scan-limits)
- reqwest 0.12.28 `ClientBuilder`: `timeout` applies from connect start until the body has finished and “Default is no timeout.” `read_timeout` resets after each successful read and “Default is no timeout.” `connect_timeout` “Default is `None`.” `pool_idle_timeout` “Default is 90 seconds” (`None` disables it). `pool_max_idle_per_host` “Default is `usize::MAX` (no limit).” — [reqwest 0.12.28 `client.rs`](https://docs.rs/reqwest/0.12.28/src/reqwest/async_impl/client.rs.html)
- Older reqwest 0.9 documented a 30-second default for the combined connect/read/write timeout and `usize::MAX` idle connections per host. That 30-second default is not what 0.12.28 documents. — [reqwest 0.9 ClientBuilder](https://docs.rs/reqwest/0.9.16/reqwest/struct.ClientBuilder.html); contradicted for current defaults by [reqwest 0.12.28 `client.rs`](https://docs.rs/reqwest/0.12.28/src/reqwest/async_impl/client.rs.html)
- hyper’s HTTP/2 server `max_concurrent_streams` “Default is 200, but not part of the stability of hyper. It could change in a future release. You are encouraged to set your own limit.” `None` removes the limit. This setting is the server advertising how many streams the peer may open. — [hyper server `http2.rs`](https://docs.rs/hyper/latest/src/hyper/server/conn/http2.rs.html)
- hyper’s HTTP/2 client `max_concurrent_streams` “only controls the maximum number of streams that can be initiated by the remote peer.” The docs’ own example: setting it to 100 “does not limit the number of concurrent streams that can be created by the caller.” The caller’s own stream cap is whatever the server sends in `SETTINGS_MAX_CONCURRENT_STREAMS`. — [hyper `client/conn/http2.rs`](https://github.com/hyperium/hyper/blob/master/src/client/conn/http2.rs)

### Inferences

- A scanner that already has a shared rate limit plus a bound on in-flight requests matches the split ZAP, Nuclei, and Burp document: threads or bulk size cap outstanding work, and a separate RPS or delay cap controls how fast new requests are released. Copying Nuclei’s 150/s or 25-wide defaults is not something the other two products recommend as a target-safety setting.
- ZAP’s deprecated inter-request sleep is explicitly called out as not enforcing a rate once many threads are in flight. A shared limiter that accounts for every send is the control they point operators to.
- reqwest’s unlimited idle-per-host pool and lack of a default total timeout mean the scanner’s own in-flight cap, body cap, and timeouts are what bound resource use. The pool will not do that by default.
- On HTTP/2, raising reqwest’s idle-connection cap does not create more parallel streams to one host. Parallelism to that host is the server’s `SETTINGS_MAX_CONCURRENT_STREAMS`, unless the client opens more than one connection on purpose.

### Gaps

- No published numeric default for ZAP requests-per-second, ZAP spider thread count on the options page, or Burp “maximum concurrent requests.”
- `Constant.getDefaultThreadCount()` was not opened in this pass, so the live integer (processors, or processors with a cap) is not quoted from source, only the 2.13 issue’s stated intent and the 2.17 fallback call.
- Nuclei’s rate-limiter implementation (token bucket versus leaky bucket, burst size) is not described in the mass-scanning page. Only the “applied just before sending” timing is.
- No current reqwest doc states a default maximum number of active (not idle) connections per host.

## How should a rate limiter interact with parallel requests?

### Takeaway

A token-bucket limiter that is safe for many waiters still only schedules start times. It does not cap how many requests are in flight, and a reservation is charged when it is taken, not when the response returns. Gate the send itself (`Wait` or sleep-then-send inside an already bounded worker) and cancel the reservation if the send is abandoned. Queueing fully built requests behind the limiter, which is what Nuclei documents, spends memory before a byte is on the wire.

### Cited Findings

- `golang.org/x/time/rate` is a token bucket. “Limiter has three main methods, Allow, Reserve, and Wait. Most callers should use Wait.” Allow returns false if no token is available. Reserve “returns a reservation for a future token and the amount of time the caller must wait before using it.” Wait “blocks until one can be obtained or its associated context.Context is canceled.” “Limiter is safe for simultaneous use by multiple goroutines.” — [golang.org/x/time/rate `rate.go`](https://github.com/golang/time/blob/master/rate/rate.go)
- `ReserveN` “returns a Reservation that indicates how long the caller must wait before n events happen. The Limiter takes this Reservation into account when allowing future events.” The documented use is to sleep `Delay()` and then act. “If you need to respect a deadline or cancel the delay, use Wait instead.” If `OK()` is false, “n exceeds the Limiter's burst size.” — [golang.org/x/time/rate `rate.go`](https://github.com/golang/time/blob/master/rate/rate.go)
- The Go wiki’s low-rate pattern takes a tick and only then starts the call: `<-throttle` followed by `go client.Call(...)`. It says a ticker is appropriate “for rates up to tens of operations per second” and “for higher rates, prefer a token bucket rate limiter such as golang.org/x/time/rate.Limiter.” The snippet does not bound how many calls are outstanding. — [Go Wiki: Rate Limiting](https://go.dev/wiki/RateLimiting)
- Nuclei applies the global rate limit “just before sending requests,” after those requests “are already prepared and are in memory waiting to be sent.” A very low `-rl` therefore raises memory as well as lowering RPS. Concurrency (`-c`, `-bs`) is a separate flag from `-rl`. — [Mass Scanning with Nuclei](https://docs.projectdiscovery.io/opensource/nuclei/mass-scanning-cli)
- Burp models the same split as two pool settings: a simultaneous-request cap, and a millisecond delay between requests. ZAP deprecated a per-request sleep because it does not enforce a rate, and points operators at the RPS rule, which is independent of thread count. — [Burp Tasks settings](https://portswigger.net/burp/documentation/desktop/settings/project/tasks); [ZAP Options Active Scan](https://www.zaproxy.org/docs/desktop/ui/dialogs/options/ascan/)
- RFC 9113 describes application-layer head-of-line blocking on HTTP/1.1 pipelining: pipelining “only partially addressed request concurrency and still suffers from application-layer head-of-line blocking,” which is why “HTTP/1.0 and HTTP/1.1 clients use multiple connections to a server to make concurrent requests.” HTTP/2 streams are “largely independent,” so “a blocked or stalled request or response does not prevent progress on other streams,” but “TCP head-of-line blocking is not addressed by this protocol.” — [RFC 9113](https://www.rfc-editor.org/rfc/rfc9113)

### Inferences

- Call `Wait` (or take the reservation and sleep) immediately before the socket write, on a worker that already holds one of the in-flight slots. Taking the reservation earlier, while the worker is still building the request or waiting on a baseline, charges the bucket and pushes every other waiter later (`ReserveN` is accounted for immediately). That is the limiter form of head-of-line blocking.
- If the context fires during `Wait`, the wait must end and the reservation must not be left outstanding, which is why the rate package tells callers who need cancellation to use `Wait` rather than `Reserve` plus an unbounded sleep.
- The in-flight cap and the rate limiter answer different questions. The Go wiki example can start one call per tick with no ceiling on replies still being read. Nuclei’s note is the other failure: the rate limiter successfully slows the wire, but the work queue in front of it still holds prepared requests. Both bounds have to exist, and the expensive object (parsed request, body buffer) should be created after a slot and a token are held, or the queue in front of the limiter has to be small.
- A single shared mutex around “check limit then send” serializes only the decision. It should not be held across the response read, or the RPS cap collapses to “one request at a time” even though the configured concurrency is higher. ZAP’s complaint about delay-between-requests is the same shape: a sleep that is not a shared account of sends does not produce the configured rate once threads overlap.

### Gaps

- The `rate.go` comments fetched here do not include the `Reservation.Cancel` body text. Cancel-on-abort is the right companion to `Reserve`, but the exact restore rules were not re-read in this pass.
- No Tokio or reqwest document was found that specifies an order between a semaphore permit and a rate-limiter reservation. The interaction above is inferred from the Go limiter contract and from Nuclei’s “limiter runs after the request is built” warning, not from a Rust HTTP guide.
- Whether ZAP’s RPS implementation is a token bucket, and whether it blocks a scanner thread or queues the message, is not stated in the Rate Limit options page.

## Body size caps, and HTTP/2 multiplexing versus many TCP connections

### Takeaway

Production scanners cap how much of a response they read or parse instead of buffering the whole body. Nuclei’s current mass-scanning doc says it reads at most 4 MB by default so a large object cannot be stored in full. HTTP/2 is specified so that many exchanges share one TCP connection; HTTP/1 clients open many connections because one exchange at a time (or pipelining) blocks. The server, not the client’s local `max_concurrent_streams`, decides how many streams the client may open, and TCP head-of-line blocking remains.

### Cited Findings

- Nuclei `-rsr` / `-response-size-read` “controls the maximum response size of http response that nuclei should read and its default value is 4MB (max).” The stated reason: a 100 MB response (the example is “a zip file or something”) is only read for the first 4 MB “to avoid DOS as data read is stored in memory.” — [Mass Scanning with Nuclei](https://docs.projectdiscovery.io/opensource/nuclei/mass-scanning-cli)
- On 3 January 2024 a Nuclei maintainer answered a “limit output size” question with CLI help text `-response-size-read` default `10485760` and `-response-size-save` default `1048576`. — [projectdiscovery discussion #4589](https://github.com/orgs/projectdiscovery/discussions/4589)
- An April 2024 Nuclei bug report logged the engine’s `maxBodylimit` as `4194304` (4 MiB) at the first assignment, then overwrote it from the template `max-size` and again from `ResponseReadSize` when that option was non-zero. So at that revision a template `max-size` did not win over the CLI read size. — [nuclei#5094](https://github.com/projectdiscovery/nuclei/issues/5094)
- ZAP spider “Maximum parse size” is “the maximum size, in bytes, that a response might have to be parsed,” so the spider can “skip big responses/files.” Zero means unlimited. The options page does not give the default integer. — [ZAP Options Spider](https://www.zaproxy.org/docs/desktop/addons/spider/options/)
- The ZAP Automation Framework spider job documents `maxParseSizeBytes` default `2621440` and calls that “2.5 Mb.” It also documents `maxDepth` default 5. — [ZAP Spider Automation](https://www.zaproxy.org/docs/desktop/addons/spider/automation/)
- RFC 9113: HTTP/2 allows “multiple concurrent exchanges on the same connection.” “A single HTTP/2 connection can contain multiple concurrently open streams, with either endpoint interleaving frames from multiple streams.” “The resulting protocol is more friendly to the network because fewer TCP connections can be used in comparison to HTTP/1.x.” “Note, however, that TCP head-of-line blocking is not addressed by this protocol.” — [RFC 9113](https://www.rfc-editor.org/rfc/rfc9113)
- `SETTINGS_MAX_CONCURRENT_STREAMS` is directional. “Initially, there is no limit to this value. It is recommended that this value be no smaller than 100, so as to not unnecessarily limit parallelism.” A client’s setting limits streams the server may open, and the server’s setting limits streams the client may open. — [RFC 9113 §5.1.2 and §6.5.2](https://www.rfc-editor.org/rfc/rfc9113)
- Initial stream and connection flow-control windows are 65,535 octets until `SETTINGS_INITIAL_WINDOW_SIZE` or `WINDOW_UPDATE`. The initial HPACK dynamic table size is 4,096 octets. — [RFC 9113](https://www.rfc-editor.org/rfc/rfc9113)
- Flow control exists so a receiver can restrict what is transmitted “to what the receiver is able to handle.” A stalled stream does not, by itself, stop other streams, but a connection-level window still applies to the whole connection. — [RFC 9113](https://www.rfc-editor.org/rfc/rfc9113)
- RFC 9113 security text: “stream creation is relatively inexpensive when compared to the creation and maintenance of a TCP connection,” and a proxy “cannot rely on SETTINGS_MAX_CONCURRENT_STREAMS alone” to limit CONNECT resource use, including TCP `TIME_WAIT` on connections it opened. — [RFC 9113 §10.5.2](https://www.rfc-editor.org/rfc/rfc9113)
- hyper’s client-side concurrent-stream setting does not cap streams the client opens; the server’s setting does. hyper’s server default advertisement is 200 and is explicitly unstable. — [hyper client http2.rs](https://github.com/hyperium/hyper/blob/master/src/client/conn/http2.rs); [hyper server http2.rs](https://docs.rs/hyper/latest/src/hyper/server/conn/http2.rs.html)
- reqwest’s pool keeps idle connections up to 90 seconds by default, with no default cap on how many idle connections exist per host. — [reqwest 0.12.28 `client.rs`](https://docs.rs/reqwest/0.12.28/src/reqwest/async_impl/client.rs.html)

### Inferences

- Capping the analyzed body (the scanner’s existing behavior) is the same idea as Nuclei’s read cap and ZAP’s parse cap: the bound is there so one large response cannot be stored whole. The two Nuclei numbers that must not be conflated are “bytes read into the matcher” and “bytes saved into the result.” The 2026 mass-scanning page states 4 MB for the read cap; the 2024 maintainer comment stated 10,485,760. The April 2024 log line showed 4,194,304 inside the engine. Treat 4 MB as the current documented read default, and do not treat the 2024 help-text line as the 2026 default.
- For one origin, HTTP/2 is the case where many in-flight requests should share one TCP connection, up to the server’s stream cap (spec recommends that cap not be under 100; it starts unlimited until the peer sends a setting). Opening one TCP connection per in-flight request is the HTTP/1 pattern the RFC describes, not the HTTP/2 one. Extra HTTP/2 connections are a workaround for a server that sets a low stream cap or for TCP head-of-line blocking, not the default the spec argues for.
- A body cap also bounds flow-control memory: unread body bytes sit in the stream window. Stopping the read at a fixed size and dropping the rest (or closing the stream) is what keeps the cap real. The RFC does not specify a scanner’s cutoff.

### Gaps

- ZAP’s desktop spider page does not state the 2,621,440 byte default; only the automation job reference does. Whether the desktop default matches was not confirmed against current spider-addon source.
- No reqwest or hyper client doc fetched here states the client’s default HTTP/2 initial stream window or whether adaptive flow control is on by default. Server docs say “if not set, hyper will use a default” without giving the client number.
- No source here says whether reqwest opens a second HTTP/2 connection to a host when the first hits the server’s stream limit.

## Which scan phases are documented as parallel, and which stay ordered?

### Takeaway

Independent fetches are documented as parallel: ZAP’s spider and per-host active-scan threads, Nuclei’s templates and targets, Burp tasks sharing a resource pool. Work that consumes an earlier response (login, CSRF, a later matcher that reads `status_code_1` / `body_2`, a recorded sequence) is documented as ordered. A crawl frontier is not documented as single-threaded; ZAP’s spider is explicitly multi-threaded and uses a shared visited-set. Baseline-versus-attack ordering inside a normal active-scan rule was not found as a written rule.

### Cited Findings

- ZAP’s spider “is multi-threaded” and the thread setting is “the maximum number of worker threads used in the crawling process.” Changing it does not affect a crawl already running. — [ZAP Options Spider](https://www.zaproxy.org/docs/desktop/addons/spider/options/)
- The spider’s visited check is shared across the crawl. Three modes change what counts as already visited: ignore query parameters, consider only the parameter name, or consider name and value. That is how parallel workers avoid fetching the same resource twice, not a single ordered walk. — [ZAP Options Spider](https://www.zaproxy.org/docs/desktop/addons/spider/options/)
- Spider limits that keep a parallel crawl from fanning out without bound: max depth (0 means unlimited; automation default is 5), max children per node (default 0, no limit), max duration in minutes (default 0, until links are exhausted), and max parse size. — [ZAP Options Spider](https://www.zaproxy.org/docs/desktop/addons/spider/options/); [ZAP Spider Automation](https://www.zaproxy.org/docs/desktop/addons/spider/automation/)
- ZAP active scan parallelizes across hosts and, within a host, across threads. Hosts-at-once falls back to 2 in 2.17.0 source. — [ZAP Options Active Scan](https://www.zaproxy.org/docs/desktop/ui/dialogs/options/ascan/); [ScannerParam.java](https://fossies.org/dox/zaproxy-2.17.0/ScannerParam_8java_source.html)
- Anti-CSRF handling “previously would have forced the scanner to only use one thread, but that is no longer the case.” With more than one thread, “you are strongly recommended to check that the anti CSRF tokens are being correctly generated,” for example by checking success and failure patterns. — [ZAP Options Active Scan](https://www.zaproxy.org/docs/desktop/ui/dialogs/options/ascan/)
- ZAP Sequence Scanner exists because “particular events or pages [must] be accessed or completed in a certain order.” “The sequence active scanner will replay the sequence it is attacking.” Sequences can assert that a replayed response body length matches within a percentage margin. — [ZAP Sequence Scanner](https://www.zaproxy.org/docs/desktop/addons/sequence-scanner/)
- Nuclei runs many templates and many targets at once (`-c` 25, `-bs` 25) and chooses template-spray specifically so one target is not hit with every template at once. Payload parallelism inside one template is `threads` in the template, else `-c`, with `-pc` default 25 when `threads` is absent. — [Mass Scanning with Nuclei](https://docs.projectdiscovery.io/opensource/nuclei/mass-scanning-cli)
- Nuclei keeps cookies across “a series of requests” so a template can “maintain a session” or “perform authenticated scans,” unless `disable-cookie: true`. Value sharing extracts from one HTTP request and reuses it in a later one, “like login, CSRF tokens.” Request-condition DSL refers to earlier responses by 1-based index (`status_code_1`, `body_2`). “Request conditions might require more memory as all attributes of previous responses are kept in memory.” — [Basic HTTP](https://docs.projectdiscovery.io/templates/protocols/http/basic-http); [HTTP Value Sharing](https://docs.projectdiscovery.io/templates/protocols/http/value-sharing)
- Nuclei `flow` runs steps conditionally in program order, for example `flow: http(1) && http(2)` so a fingerprint request runs before a second request. Multi-protocol templates “are executed in serial i.e one after another” and “in order of protocols defined in template.” — [Flow Protocol](https://docs.projectdiscovery.io/templates/protocols/flow); [Multi-protocol](https://docs.projectdiscovery.io/templates/protocols/multi-protocol)
- Nuclei `threads` on a template is also how connection pooling is turned on for payload attacks. `Connection: Close` cannot be used with that pooling mode. That is parallelism for many payloads, not ordering between dependent requests. — [Connection Tampering](https://docs.projectdiscovery.io/templates/protocols/http/connection-tampering)
- Burp lets several scan and audit tasks run together under one pool, with different concurrency for a background crawl-and-audit versus a priority audit of selected requests. Passive crawl tasks do not use resource pools. — [Task execution settings](https://portswigger.net/burp/documentation/desktop/running-scans/live-tasks/task-execution-settings); [Managing resource pools](https://portswigger.net/burp/documentation/desktop/running-scans/managing-resource-pools)
- Google’s robots.txt documentation: Google supports `user-agent`, `allow`, `disallow`, and `sitemap`, and “other fields such as `crawl-delay` aren't supported.” It points at RFC 9309 as the standard. — [How Google interprets the robots.txt specification](https://developers.google.com/crawling/docs/robots-txt/robots-txt-spec)
- RFC 9309 (September 2022, Proposed Standard) specifies the Robots Exclusion Protocol for which URIs crawlers may access. This pass did not find `crawl-delay` in the sections retrieved; Google’s interpretation page is the explicit statement that the field is unsupported. — [RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html); [Google robots.txt spec](https://developers.google.com/crawling/docs/robots-txt/robots-txt-spec)

### Inferences

- Independent GETs of known paths match the phase these products already parallelize: spider workers, per-host scan threads, Nuclei payload/template/target concurrency, Burp tasks in one pool. The politeness control on that phase is the shared RPS limit and the in-flight cap, not a return to one-at-a-time.
- A crawl frontier in ZAP is parallel, with a shared visited-set and optional depth and fan-out caps. Ordering is the wrong model for that phase. What has to stay serialized is any later request whose URL, cookie, or CSRF token is produced by an earlier response, and any check that compares a replay to a previous response (ZAP’s sequence length assertion; Nuclei’s indexed matchers).
- Authenticated session setup is ordered only for the login or token exchange itself. After a session exists, ZAP will scan “as a user” with the normal thread pool, and it no longer drops to one thread just because anti-CSRF is on. Correctness then depends on each thread refreshing a token rather than on a global lock. Nuclei’s cookie jar across a series of requests is the same idea at template scope.
- `crawl-delay` is not a concrete rule a scanner can implement from RFC 9309 or from Google’s current documentation. Politeness toward a target that does not publish a rate has to be the scanner’s own RPS and concurrency caps. Backing off when the target returns 429 or 503 is the behavior Burp documents.

### Gaps

- No ZAP or Burp page found in this pass says that a differential check (baseline response, then a mutated request, then a compare) must run on one thread. Sequence replay and Nuclei indexed matchers are the documented ordered compares.
- Nuclei does not state, on the pages read, whether several HTTP requests listed in one template block without `flow` run strictly one after another when `threads` is also set. Ordered behavior is documented for cookies-across-a-series, value sharing, request-condition indexes, `flow`, and multi-protocol serial execution.
- Bing’s numeric `crawl-delay` range was only seen on a secondary SEO page and is not cited. No official crawler document in this pass states a required delay in seconds.

## Measured memory costs (2024–2026)

### Takeaway

No 2024–2026 writeup with a stated measurement method was found for bytes of RAM per TCP or TLS connection, or for steady-state body-buffer cost. The usable figures are product formulas and protocol constants: Nuclei’s stated heap relationship to concurrency times the read cap, a 4 MB default read cap, ZAP’s 2.5 MB parse default in the automation reference, and HTTP/2’s 65,535-octet initial windows. Those are not bench measurements.

### Cited Findings

- Nuclei documents “a direct correlation between concurrency and memory usage” and states that “at any moment heap memory of Nuclei is `1-1.5x x (concurrency * response-size-read)`.” The same section says the read cap’s default is 4 MB so a 100 MB body is not stored whole. No workload, allocator, or measurement procedure is given for the 1–1.5× factor. — [Mass Scanning with Nuclei](https://docs.projectdiscovery.io/opensource/nuclei/mass-scanning-cli)
- The same page names other memory drivers without byte counts: template-spray holds a separate target chunk per template; `-stream` “may lead to high memory usage” in template-spray because of marshal overhead and per-template copies; a low `-rl` holds prepared requests; a high `-timeout` “might cause high memory usage”; `-nmhe` keeps failing hosts in memory; Go’s HTTP stack “focuses on reusing memory than freeing it,” so a low GC memory limit is discouraged. — [Mass Scanning with Nuclei](https://docs.projectdiscovery.io/opensource/nuclei/mass-scanning-cli)
- Nuclei request-condition checks “might require more memory as all attributes of previous responses are kept in memory.” — [Basic HTTP](https://docs.projectdiscovery.io/templates/protocols/http/basic-http)
- ZAP automation documents a 2,621,440-byte (described as 2.5 Mb) default maximum response size the spider will parse. The desktop page says zero means unlimited and that the cap exists so big responses are skipped. — [ZAP Spider Automation](https://www.zaproxy.org/docs/desktop/addons/spider/automation/); [ZAP Options Spider](https://www.zaproxy.org/docs/desktop/addons/spider/options/)
- RFC 9113 initial flow-control window is 65,535 octets for a new stream and 65,535 octets for the connection, until the peer raises it. Initial HPACK dynamic table size is 4,096 octets. The RFC does not convert those protocol windows into process RSS. — [RFC 9113](https://www.rfc-editor.org/rfc/rfc9113)
- RFC 9113 says creating a stream is “relatively inexpensive” next to creating a TCP connection, and that `SETTINGS_MAX_CONCURRENT_STREAMS` does not by itself bound proxy memory for CONNECT because the outbound TCP connection can outlive the stream (`TIME_WAIT`). No byte cost is stated. — [RFC 9113 §10.5.2](https://www.rfc-editor.org/rfc/rfc9113)
- reqwest 0.12.28 does not document a per-connection memory cost. It documents an idle timeout of 90 seconds and no limit on idle connections per host, which is a retention policy rather than a measured size. — [reqwest 0.12.28 `client.rs`](https://docs.rs/reqwest/0.12.28/src/reqwest/async_impl/client.rs.html)

### Inferences

- The only sizing relation a report can repeat without inventing a benchmark is Nuclei’s: heap on the order of one to one-and-a-half times concurrency times the body-read cap, plus extra copies if each worker retains a previous response for a comparison. For a scanner that already caps the analyzed body, the cap is the term that dominates, not an unpublished “cost of a socket.”
- Because the 1–1.5× line has no method, it should be labeled a vendor estimate. It is still the most concrete 2024–2026 statement found, and it matches the design they shipped (read cap default 4 MB, concurrency default 25, rate limit applied only after the request exists in memory).
- Protocol windows are lower bounds on data that may be in flight, not on allocator overhead. 65,535 octets per new stream is the spec default until `WINDOW_UPDATE` / `SETTINGS_INITIAL_WINDOW_SIZE`. Implementations may raise it; this pass did not confirm hyper’s client default.

### Gaps

- No credible 2024–2026 measurement, with a method, of resident memory per TLS connection or per idle pooled connection was found. Blog figures without a method were skipped on purpose.
- A June 2025 Red Hat article describes Apache `httpd` worker RSS growth while proxying repeated HTTP/2 requests on one connection, but the analysis is subscriber-only. The public `ps` lines were not used as a cost number.
- Nuclei’s 1–1.5× formula does not define which concurrency it multiplies (`-c`, `-bs`, or `-c` times `-bs`). The page writes “concurrency” after discussing several different concurrency flags.
