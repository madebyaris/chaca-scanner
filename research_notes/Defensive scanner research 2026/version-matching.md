# Version and advisory matching in Grype, Trivy, osv-scanner, and Dependency-Check

Research date: 12 November 2026. Scope is how these scanners identify a product, compare a detected version with a published advisory, and what a finding contains. No exploit procedures were collected. These tools are software-composition and image/lockfile scanners. None of the official pages reviewed describe ingesting an HTTP `Server`, `X-Powered-By`, or meta-generator banner.

## How does each tool identify a product and compare versions?

### Takeaway

Grype, Trivy, and osv-scanner match an ecosystem package name (usually a PURL or lockfile/OS package coordinate) against that ecosystem’s advisory, and only then compare versions with an ecosystem-specific ordering. CPE is a second, often disabled, identity. Dependency-Check does the reverse: it guesses a CPE from file evidence and then attaches every NVD CVE recorded for that CPE. None of the four publish a scheme literally named `generic` in user docs; Trivy’s source calls its semver-like comparer `GenericComparer`, and the OSV schema’s non-semver range type is `ECOSYSTEM`.

### Cited Findings

- Grype accepts an image, a directory, a file, a Syft SBOM, a Zarf archive, a newline-separated PURL file, a single PURL, a newline-separated CPE file, or a single CPE. Input is checked for PURL format first, then CPE, before other target types. A PURL is `pkg:<type>/<namespace>/<name>@<version>?<qualifiers>#<subpath>`. Documented single-PURL example: `pkg:apk/openssl@3.2.1?distro=alpine-3.20.3`. CPE 2.2 and 2.3 are both accepted, for example `cpe:/a:apache:log4j:2.14.1` and `cpe:2.3:a:apache:log4j:2.14.1:*:*:*:*:*:*:*`. The docs say to use CPE for legacy identifiers or to test a CVE that references a CPE. — [Grype CLI reference](https://oss.anchore.com/docs/reference/grype/cli/); [Supported scan targets](https://oss.anchore.com/docs/guides/vulnerability/scan-targets)
- Grype’s `db search` looks up affected packages by name, PURL, or CPE, and the CLI explicitly says version is not considered for a PURL search and version/update is not considered for a CPE search. That is the search command, not the scan matcher. — [Grype CLI reference](https://oss.anchore.com/docs/reference/grype/cli/)
- Default Grype configuration turns CPE matching off for java, dotnet, golang, javascript, python, ruby, rust, hex, and dpkg (`using-cpes: false`). It is on for `jvm` and `stock`. A separate flag controls CPE matching for the Go standard library (`always-use-cpe-for-stdlib: false`). — [Grype configuration reference](https://oss.anchore.com/docs/reference/grype/configuration/)
- Grype’s version package (source, main branch as fetched 12 November 2026) names these formats, in order: Unknown, Semantic, Apk, Deb, Maven, RPM, Python, KB, Gem, Portage, Go, JVM, Bitnami, Pacman. There is no constant named `generic` or `semver`; the semver-like name in this file is `Semantic`. — [grype/version/format.go](https://raw.githubusercontent.com/anchore/grype/main/grype/version/format.go)
- An rpm match record cited in a Grype bug shows the rpm matcher comparing a package version that includes an epoch (`0:1.40.16-15.el8_9` in the failing case) with a constraint written as `< 1:1.32.10-4.el8 (rpm)`. The report’s point is that a missing epoch changes the comparison. — [anchore/grype#2170](https://github.com/anchore/grype/issues/2170)
- A 2026 Grype change maps selected CPEs onto ecosystem package specifiers so a match can be raised as an affected package even when CPE matching is disabled for that ecosystem. The author describes full CPE matching as a “false positive tsunami.” — [anchore/grype#3332](https://github.com/anchore/grype/pull/3332)
- Trivy vulnerability detection is package detection. Documented classes are OS packages (container images, VM images, running hosts), language-specific packages, non-packaged software (Sigstore Rekor SBOM, Go binaries with module info, Rust binaries with embedded info, SBOM embedded in an image), and Kubernetes components. For packages installed by `dpkg`, `yum`, `apk`, and similar, Trivy uses only the advisory database of that OS vendor. A Python package installed by yum on Amazon Linux is matched to ALAS; the same package installed by pip is matched to GitLab and GitHub advisory databases. — [Trivy vulnerability scanning](https://github.com/aquasecurity/trivy/blob/main/docs/guide/scanner/vulnerability.md)
- Trivy states that this vendor-advisory choice matters because “OS vendors usually backport upstream fixes, and the fixed version can be different from the upstream fixed version.” — [Trivy vulnerability scanning](https://github.com/aquasecurity/trivy/blob/main/docs/guide/scanner/vulnerability.md)
- Trivy’s language driver selects both an OSV ecosystem and a comparer from the package type. Lines fetched from `driver.go` assign RubyGems to `rubygems.Comparer`, Cargo, Composer, and Go to `compare.GenericComparer`, and Maven (Jar, Pom, Gradle, Sbt) to `maven.Comparer`. The same file imports `compare/npm` and `compare/pep440`. `GenericComparer` is commented as “a comparer for semver-like versioning.” SemVer build metadata is not significant for precedence unless an option enables node-semver build ordering (`1.2.3` < `1.2.3+build.1` < `1.2.3+build.2` < `1.2.4`). — [compare.go](https://raw.githubusercontent.com/aquasecurity/trivy/main/pkg/detector/library/compare/compare.go); [driver.go](https://raw.githubusercontent.com/aquasecurity/trivy/main/pkg/detector/library/driver.go)
- When a language package version is a range rather than one version (`package-a: ">=3.0"`), Trivy skips detection for that package. If a lockfile has fixed versions, those are used. `--detection-priority comprehensive` instead uses the minimum version in the range, which the docs say can add false positives. — [Trivy vulnerability scanning](https://github.com/aquasecurity/trivy/blob/main/docs/guide/scanner/vulnerability.md)
- osv-scanner is two steps: extract packages from a project, image, or other target, then match them to a vulnerability database. Source scanning reads lockfiles and manifests. The docs say to prefer a resolved lockfile for the versions actually selected; a fully pinned manifest such as `pip freeze` output is the fallback; manifests “can declare version ranges and do not necessarily record the versions installed,” and extraction from manifests is best-effort and ecosystem-specific. — [OSV-Scanner usage](https://google.github.io/osv-scanner/usage/); [Supported artifacts and manifests](https://google.github.io/osv-scanner/supported-languages-and-lockfiles/)
- The OSV record identifies the package by required `ecosystem` and `name`, plus optional `purl`. Ecosystem defines how `name` is interpreted. A wildcard name `*` means all packages in that ecosystem. Affectedness is: the version is listed in `versions`, or it falls inside any `ranges` entry. — [OSV schema](https://ossf.github.io/osv-schema/); [schema.md evaluation](https://raw.githubusercontent.com/ossf/osv-schema/main/docs/schema.md)
- OSV range `type` must be one of three values. `SEMVER`: introduced and fixed are SemVer 2.0.0 versions with no leading `v`, ordered by SemVer section 11; ranges should not overlap. Ecosystems that merely recommend SemVer without enforcing it should use `ECOSYSTEM` instead. `ECOSYSTEM`: introduced and fixed are “arbitrary, uninterpreted strings specific to the package ecosystem, which does not conform to SemVer 2.0’s version ordering.” The schema recommends also listing `versions` because an ecosystem-independent tool may be unable to evaluate the range; osv.dev fills that list for supported ecosystems during ingestion. `GIT`: introduced and fixed are full-length commit hashes; the commit graph is required, and `u < v` means `u` is an ancestor of `v`. — [schema.md ranges](https://raw.githubusercontent.com/ossf/osv-schema/main/docs/schema.md)
- OSV range events are a timeline. Exactly one of `introduced`, `fixed`, `last_affected`, or `limit` is allowed per event. `introduced: "0"` sorts before every other version. `limit: "*"` means infinity, and a missing limit implies `{ "limit": "*" }`. There must be at least one `introduced`. A version is vulnerable only while it is at or after `introduced` and strictly before `fixed` (the comparison is `v >= fixed` turns vulnerable off). `last_affected` is a ceiling inclusive of that version (`v > last_affected` turns vulnerable off) and the schema says it can cause false negatives, so `fixed` is preferred. Those version strings “are not guaranteed to exactly match versions of the package found in the upstream package repository” because they may be normalized or have build metadata stripped. — [schema.md events and evaluation](https://raw.githubusercontent.com/ossf/osv-schema/main/docs/schema.md)
- osv.dev’s own issue tracker, as of January 2025, describes three query methods: semver ranges plus a generic affected-version check; non-semver ecosystems that have a comparer (Alpine, AlmaLinux, Debian, Maven, NuGet, PyPI, Red Hat, Rocky Linux, RubyGems, SUSE, Ubuntu, and others listed there); and non-semver ecosystems without a comparer, which match only an enumerated affected version. A June 2026 Cloudsmith changelog says Debian, Alpine, PyPI, and the same family of ecosystems are now matched against ecosystem-native OSV ranges, “building on existing coverage for SemVer-based ranges.” — [google/osv.dev#3063](https://github.com/google/osv.dev/issues/3063); [Cloudsmith changelog, 16 June 2026](https://cloudsmith.com/changelog/vulnerability-detection-now-covers-ecosystem-native-osv-advisories)
- Dependency-Check collects three kinds of evidence from scanned files: vendor, product, and version. The Jar analyzer reads the manifest, `pom.xml`, and package names. Evidence is scored low, medium, high, or highest. CPE data from the NVD API is stored in a Lucene index. Evidence is queried against that index; a hit adds a CPE identifier, and CVEs associated with that CPE are added to the report. The CPE’s confidence equals the lowest confidence of the evidence used to identify it. The documented CPE reading is `cpe:/[Entry Type]:[Vendor]:[Product]:[Version]:[Revision]:…`. The worked example is exact NVD criteria such as `cpe:2.3:a:django_project:django:0.91:*:*:*:*:*:*:*`. The project states it does not use file hashes, because a from-source build would not match a published hash. — [How does dependency-check work?](https://dependency-check.github.io/DependencyCheck/general/internals.html); [project README](https://github.com/dependency-check/DependencyCheck)
- The same internals page says both false positives and false negatives may exist. The README’s one-sentence method is: determine whether a dependency has a CPE, and if so link the associated CVE entries. — [Internals](https://dependency-check.github.io/DependencyCheck/general/internals.html); [README](https://github.com/dependency-check/DependencyCheck)

### Inferences

- For a web fingerprint, the closest supported input is not a header string. It is an operator-built PURL or CPE that Grype will scan as a literal (for example an apk PURL with a distro qualifier, or a CPE whose version field is the banner version). That still uses the scanner’s package or CPE matcher; it does not add distro-backport knowledge the banner does not contain.
- Grype’s scheme list and Trivy’s language comparers line up with the requested names only partly. Semantic / `GenericComparer` / OSV `SEMVER` cover semver. Grype source names Apk, Deb, RPM, and Maven. Trivy documents OS-vendor advisories rather than publishing user-facing scheme names deb, rpm, and apk. OSV `ECOSYSTEM` is the documented bucket for Debian, RPM, Alpine, Maven, and other non-enforced orderings, not a scheme named `generic`.
- Dependency-Check’s published method is identity-first (vendor + product via fuzzy evidence) and then “this CPE’s CVEs.” The internals page does not describe a separate semver, deb, rpm, apk, or maven comparator.

### Gaps

- The fetched Trivy `driver.go` fragment does not show the comparer assigned to npm, Yarn, pnpm, or the PEP 440 package, only that those packages are imported and that the npm case begins after the Maven case. OS-package comparers (deb, rpm, apk) were not opened; only the advisory-selection rule is documented.
- Dependency-Check’s internals example uses exact CPE version strings. This research did not confirm whether the current release also applies NVD `versionStartIncluding` / `versionEndExcluding` range fields, and no Dependency-Check page named a version scheme.
- Which Grype matcher binds which `Format` constant (for example whether the apk matcher always uses `ApkFormat`) was not re-read from each matcher file. Only the format inventory and one rpm constraint example were verified.

## What does a finding contain, and what is omitted?

### Takeaway

All four report an identifier, the package or file that matched, a severity, and either a fixed version or an explicit “no fix.” They do not report exploit steps, and they do not treat a missing fix as proof of safety. Severity is taken from the advisory source that was matched, not invented from the product banner. Several fields that matter for a header scan — distro revision, match confidence, and whether the identifier is a CVE or a vendor/GHSA id — are present only in some tools.

### Cited Findings

- Grype’s table columns are NAME, INSTALLED, FIXED-IN, TYPE, VULNERABILITY, SEVERITY, EPSS (score and percentile), and RISK. TYPE is the package type (`apk`, `deb`, `rpm`, `npm`, `python`, `java-archive`, and similar). SEVERITY values shown are Critical, High, Medium, Low, Negligible, and Unknown. FIXED-IN is the fixing version, the text `(won't fix)` when the vendor will not fix it, or empty when no fix is available. The example row `libcrypto1.1  1.1.1k-r0` with an empty FIXED-IN is still listed as a finding. Default vulnerability ids for npm can be GHSA ids; `--by-cve` prints the CVE instead. JSON is described as “complete structured data with all match details.” SARIF and Go templates are the other formats. An annotations column is conditional. — [Understanding Grype results](https://oss.anchore.com/docs/guides/vulnerability/interpreting-results/)
- A Grype JSON `matchDetails` object cited in a CPE false-positive report contains `type` (`cpe-match`), `matcher` (`java-matcher`), `searchedBy` (namespace `nvd:cpe` and the CPE that was searched), and `found` (`vulnerabilityID`, `versionConstraint`, and the CPE that hit). Another report shows `type` `exact-direct-match`, `matcher` `rpm-matcher`, and `found.versionConstraint`. A separate report shows GHSA and CVE rows for the same Maven artifact, with the GHSA record pointing at the CVE under `relatedVulnerabilities`. — [anchore/grype#1349](https://github.com/anchore/grype/issues/1349); [anchore/grype#2170](https://github.com/anchore/grype/issues/2170); [anchore/grype#973](https://github.com/anchore/grype/issues/973)
- Trivy’s table columns are LIBRARY, VULNERABILITY ID, SEVERITY, INSTALLED VERSION, FIXED VERSION, and TITLE. Severity is taken from the selected data source, not from NVD by default. Documented example: CVE-2023-0464 is HIGH in NVD and Low in Red Hat, and Trivy shows Low. If that source has no severity, Trivy maps a CVSS base score: 0.1–3.9 Low, 4.0–6.9 Medium, 7.0–8.9 High, 9.0–10.0 Critical. If CVSS is also missing, it falls back to NVD. If NVD has not scored it yet, Trivy uses another vendor’s rating so the result is not left UNKNOWN; the preference order is in trivy-db. If no vendor has a severity, the severity is UNKNOWN. JSON includes `SeveritySource` (for example `"debian"`) and `VendorSeverity` (numeric: 0 Unknown, 1 Low, 2 Medium, 3 High, 4 Critical). — [Trivy vulnerability scanning](https://github.com/aquasecurity/trivy/blob/main/docs/guide/scanner/vulnerability.md)
- Trivy’s own fill logic sets status to fixed when `FixedVersion` is non-empty; otherwise an unknown status becomes affected. Vendor status is kept when the vendor provides one (Red Hat is the example). A Debian discussion shows a JSON finding with `VulnerabilityID`, `PkgName`, `PkgIdentifier.PURL`, `InstalledVersion`, `Status` (`affected`), `SeveritySource`, `PrimaryURL`, `DataSource` (id, name, URL), `Title`, and `Description`. Unfixed issues can be hidden with `--ignore-unfixed`; that is a filter, not a statement that they are unfixed in the record. — [Trivy vulnerability.go](https://fossies.org/linux/trivy/pkg/vulnerability/vulnerability.go); [aquasecurity/trivy discussion #7014](https://github.com/aquasecurity/trivy/discussions/7014); [Trivy vulnerability scanning](https://github.com/aquasecurity/trivy/blob/main/docs/guide/scanner/vulnerability.md)
- osv-scanner’s table, for each finding, shows OSV URL, CVSS (v2 or v3, calculated from `severity[].score`), ecosystem, package name, installed version, fixed version, and source path (lockfile or SBOM). No fix is printed as `--`. The vertical format also prints the advisory summary, a severity string, and a “Minimal Fix Version.” Image layer scans add the layer that introduced the package, layer history and commands, base images, and the OS/distro. HTML output adds the full advisory entry plus filters for severity, package, id, importance, and fix availability. Release v2.7.0 (12 October 2026) added package URLs to JSON output when a PURL is available. — [OSV-Scanner output](https://google.github.io/osv-scanner/output/); [osv-scanner v2.7.0 notes](https://github.com/google/osv-scanner/releases)
- An OSV record itself has `id`, `modified`, `published`, optional `withdrawn`, `aliases`, `related`, `summary`, `details`, `severity` entries (`type`, `score`, optional `source`), `affected` (package, ranges, versions), and `references` (`type` and URL). Severity types defined on the schema page include `CVSS_V2`. The schema says it only standardizes fields that must be shared; everything else belongs in `ecosystem_specific` or `database_specific`, and `database_specific` does not affect the evaluation algorithm. — [OSV schema](https://ossf.github.io/osv-schema/); [schema.md](https://raw.githubusercontent.com/ossf/osv-schema/main/docs/schema.md)
- Dependency-Check’s summary table columns are Dependency (file name), CPE, GAV (Maven group, artifact, version), Highest Severity, CVE Count, CPE Confidence, and Evidence Count. The report text tells the reader to check that the CPE is right before trusting the CVEs, and to suppress a wrong CPE. It does not list a fixed-version column in that summary. False positives are described as primarily wrong CPE values. One class the project says is often mistaken for a false positive: an old database driver whose CPE and CVEs are for the database server, which the project treats as a hint that an old server may be present, not as a finding to drop automatically. — [How to read the reports](https://dependency-check.github.io/DependencyCheck/general/thereport.html)

### Inferences

- “Deliberately omit” is visible in the defaults, not in a single denial list. Trivy omits third-party repository packages from official-advisory matching and omits unpinned versions unless comprehensive mode is on. Grype omits CPE matches for most language ecosystems and for dpkg unless configured. osv-scanner omits a fix version rather than guessing one (`--`). Dependency-Check omits hash identity and omits any claim that the CPE is correct; confidence is part of the finding so a human can reject it. None of the output pages describe including proof-of-concept code, exploit steps, or a reachability proof in the default finding.
- A header-only finding that copied these shapes would still be missing what the tools use as identity: Grype TYPE plus distro-qualified package, Trivy `DataSource` and PURL, osv-scanner ecosystem plus lockfile path, Dependency-Check evidence and CPE confidence. A CVE id and a severity with no source would not match how Trivy or osv-scanner attribute severity.

### Gaps

- The Grype “Understanding results” page fetched here does not enumerate every JSON key (references, CVSS vector, URLs). Those keys were only seen inside GitHub issue excerpts (`matchDetails`, `relatedVulnerabilities`), which are examples, not the schema reference.
- Dependency-Check’s detail pane almost certainly lists NVD links per CVE, but the “How to read the reports” page that was fetched does not say so, and it does not say the report contains or omits a fixed version. Absence from the summary column list is not a written statement that the detail view has no references.
- Whether osv-scanner’s default finding includes the OSV `references` array, or only the osv.dev URL, is documented for the table (URL, not the array) and for HTML (“full vulnerability advisory entries”). The JSON field list was not fully quoted.

## How do they treat end-of-life software with no new CVE?

### Takeaway

These scanners report published advisories whose affected range contains the detected package version. OpenSSL’s own posts define 1.1.1 and 3.0 end of life as “no further publicly available security fixes,” which is a support boundary, not a CVE. No page reviewed for Grype, Trivy, osv-scanner, or Dependency-Check says they emit a finding only because a branch is end of life. Upstream EOL also does not equal distro EOL.

### Cited Findings

- OpenSSL 1.1.1, an LTS release from 11 September 2018, reached end of life on 11 September 2023 and “will no longer receive publicly available security fixes.” The same post says a copy obtained from an OS vendor or another third party can have a different support period, and that readers must check that vendor. Extended fixes after public EOL exist only under a premium support contract, with no defined end date. The final public release announced for the series was 1.1.1w, called the final public release, on 11 September 2023. — [OpenSSL 1.1.1 End of Life](https://www.openssl.org/blog/blog/2023/09/11/eol-111); [Forthcoming OpenSSL 1.1.1w](https://mta.openssl.org/pipermail/openssl-users/2023-September/016690.html)
- OpenSSL Library 3.0 reached end of life on 7 September 2026. The project states it issues no further fixes for the 3.0 line, security fixes included. The release strategy had carried that date since 3.0 shipped. Public support for an LTS release is five years. — [OpenSSL Library, 16 September 2026](https://openssl-library.org/post/2026-09-16-eol30/); [OpenSSL Corporation, 16 September 2026](https://openssl-corporation.org/blog/openssl-3-0-end-of-life.html)
- As of the release strategy page updated 5 November 2026, versions still in support include 4.1 until 2027-11-23, 4.0 until 2027-05-14, and 3.5 (LTS) until 2030-04-08. Versions 3.0, 1.1.1, and 1.0.2 are no longer supported; extended support that supplies security fixes for those versions is a paid contract. The 16 September 2026 library post names 4.0 support until 14 May 2027 and 3.5 until 8 April 2030, and says 3.0’s latest public release in the endoflife.date table is 3.0.22 (25 August 2026). endoflife.date lists 1.1.1’s latest as 1.1.1w (12 September 2023) and its public support as ended 11 September 2023. — [Release strategy](https://openssl.org/policies/releasestrat.html); [OpenSSL 3.0 End of Life](https://openssl-library.org/post/2026-09-16-eol30/); [endoflife.date/openssl](https://endoflife.date/openssl)
- From 3.0.0 onward, OpenSSL versions are `MAJOR.MINOR.PATCH`. The same major guarantees API/ABI compatibility. Previously compatibility was per `MAJOR.MINOR`. — [endoflife.date/openssl](https://endoflife.date/openssl)
- FIPS is a separate date from the software EOL. OpenSSL Corporation states that on 21 September 2026 the CMVP moves remaining FIPS 140-2 validations, including OpenSSL FIPS Provider certificate #4282 (the provider that ships with 3.0), to the Historical List. That is described as a validation-status change. The FIPS 140-3 replacement cited is certificate #4985, validated through March 2030. — [FIPS 140-2 sunsets in September 2026](https://openssl-corporation.org/blog/fips-140-2-sunsets-september-2026.html)
- Grype’s documented result for an unfixed issue is still a vulnerability row with an empty FIXED-IN or `(won't fix)`, tied to a vulnerability id such as a CVE. The worked table includes `libcrypto1.1` at `1.1.1k-r0` only in connection with CVE ids, not with an “end of life” id. — [Understanding Grype results](https://oss.anchore.com/docs/guides/vulnerability/interpreting-results/)
- Trivy’s status for a row with no fixed version is affected (unless the vendor supplied another status). Hiding those rows is an operator flag. Nothing in the vulnerability guide says an unsupported upstream branch is itself a detection. — [Trivy vulnerability scanning](https://github.com/aquasecurity/trivy/blob/main/docs/guide/scanner/vulnerability.md); [vulnerability.go](https://fossies.org/linux/trivy/pkg/vulnerability/vulnerability.go)
- OSV evaluation returns true only when the package matches and the version is inside `versions` or a range. An advisory with no range and no version list does not match. `last_affected` marks versions above that ceiling as unaffected even when that can be a false negative. — [schema.md evaluation](https://raw.githubusercontent.com/ossf/osv-schema/main/docs/schema.md)

### Inferences

- After 7 September 2026, a scanner built like these four will keep reporting 3.0 only where an existing advisory’s range still contains the detected version. It will not grow new CVE rows for flaws that upstream declines to publish a public fix for, unless some other database (a distro tracker, a GHSA, a commercial feed) publishes a record these tools ingest. EOL without a new CVE is invisible to the matchers as documented.
- A banner that reads `OpenSSL/1.1.1f` or a 3.0.x version is an upstream version string. The 1.1.1 EOL post says the OS vendor’s support period may differ, so treating that banner as “unsupported, therefore vulnerable” contradicts the upstream instruction to check the vendor. That is the same reason Trivy refuses to apply upstream fixed versions to distro packages.
- Paid “extended support” is explicitly not a public release stream. A public advisory database cannot see those fixes, so a scanner cannot distinguish a commercially patched 3.0 from an unpatched 3.0 by version number alone.

### Gaps

- No Grype, Trivy, osv-scanner, or Dependency-Check document reviewed here mentions OpenSSL 3.0’s 7 September 2026 EOL or an end-of-life database. Absence of a sentence is not a formal “we will never flag EOL,” but no positive EOL feature was found.
- This research did not query a live Grype or Trivy database for which OpenSSL 3.0.x or 1.1.1w version ranges are currently marked affected, so no affected-version bound from those tools is stated.
- endoflife.date is a community lifecycle table. It agrees with OpenSSL’s dates for 1.1.1 and 3.0, but it is not the scanner vendor and it is not the OpenSSL project.

## What false-positive patterns are documented for server banners?

### Takeaway

The scanner vendors document false positives from applying an upstream or NVD version range to a distro package that has backported the fix, and from loose CPE identity. They do not document HTTP banner parsing. nginx’s own docs document a second versioning trap: stable and mainline are separate branches, security fixes are backported onto stable, and the branch is the middle number (odd mainline, even stable). A header can also name a module, such as OpenSSL, rather than the server package.

### Cited Findings

- Trivy: using the upstream fixed version for an OS package is wrong because vendors backport fixes and the fixed package version differs. Trivy therefore selects the OS vendor advisory for `dpkg`, `yum`, `apk`, and the other package managers it lists. It also skips packages it classifies as third-party repositories (examples: EPEL, Remi, Docker, NVIDIA), because official OS advisories do not track them and scanning them against those advisories “would lead to false positives.” Detection of third-party packages is heuristic (RPM vendor, APT source). Unrecognized third-party packages are still scanned and “could result in false positives.” Packages from a lesser-known but legitimate vendor can be skipped, which is a false negative. — [Trivy vulnerability scanning](https://github.com/aquasecurity/trivy/blob/main/docs/guide/scanner/vulnerability.md)
- Trivy’s stated detection bias is precision: “minimize false positives while potentially accepting some false negatives.” A Debian case discussed by users shows the complementary miss: a bookworm image with a newer sudo taken from testing stayed `affected` because the bookworm tracker had no fixed version, so a newer upstream version was not treated as a fix. Maintainer comments on a Rocky Linux report say `7.61.1-33.el8` and `7.61.1-33.el8_9.5` are different versions under the versioning Trivy applies; the user had expected the dist tag to collapse them. — [Trivy vulnerability scanning](https://github.com/aquasecurity/trivy/blob/main/docs/guide/scanner/vulnerability.md); [discussion #7014](https://github.com/aquasecurity/trivy/discussions/7014); [discussion #6488](https://github.com/aquasecurity/trivy/discussions/6488)
- Grype: a merged change skips CPE matching for linux-kernel packages on distros that have reliable distro data, “to avoid false positives from nvd's version ranges not covering backported fixes.” Kernel findings are left to the dpkg or rpm matcher. The example in the pull request is CVE-2023-2163, described there as fixed in `5.15.0-70.77~20.04.1` while the installed package is `5.15.0-164`. An open Grype issue says NVD configurations that AND a product CPE with another product are not honored, so a Tomcat CPE matched CVE-2016-5425 even though NVD required an additional product. Grype issue discussion of indirect upstream matching says a binary package can inherit every CVE of its source package (`php8.3-xml` inheriting `php8.3`, `python-perf` inheriting the kernel), which maintainers describe as a large source of false positives. — [anchore/grype#3129](https://github.com/anchore/grype/pull/3129); [anchore/grype#1349](https://github.com/anchore/grype/issues/1349); [Anchore community thread](https://anchorecommunity.discourse.group/t/indirect-matches-vulnerabilities-affecting-the-upstream-packages-are-sometimes-too-broad/523)
- Grype defaults already keep CPE matching off for dpkg and for most language ecosystems. The 2026 CPE-to-package mapping change is explicitly an alternative to turning CPE matching on, which the author calls a false-positive flood. — [Grype configuration](https://oss.anchore.com/docs/reference/grype/configuration/); [anchore/grype#3332](https://github.com/anchore/grype/pull/3332)
- Dependency-Check warns that false positives are mostly wrong CPEs, and that confidence is the lowest evidence score used. The report instructions say a wrong CPE is usually obvious and should be suppressed. A 2025 report against the tool shows low-confidence matches of unrelated packages whose names contain “Redis” to `cpe:2.3:a:redis:redis`, and a Composer package `phpunit/php-timer` matched to a PHP CPE. Those are user reports, not a design note. The project’s own “old database driver” note is the documented pattern of a client library inheriting a server product’s CVEs. — [How to read the reports](https://dependency-check.github.io/DependencyCheck/general/thereport.html); [Internals](https://dependency-check.github.io/DependencyCheck/general/internals.html); [dependency-check#7444](https://github.com/dependency-check/DependencyCheck/issues/7444)
- nginx documents two branches, not one line. Mainline is updated about every one or two months with features, bug fixes, and security fixes, and “always has an odd middle number, for example, 1.27.X.” Stable is updated about once a year, or as needed, for critical bug fixes or security fixes “that are always backported from the Mainline version,” and “is always even-numbered, for example, 1.28.X.” Mainline is recommended for production unless stability requirements say otherwise. Distribution packages “may be outdated,” F5/nginx does not verify a distro package’s contents or update frequency, and “some Linux distros, especially those focused on long-term support, provide the Stable version only.” Official packaging uses separate `nginx-stable` and `nginx-mainline` repositories. — [Installing NGINX Open Source](https://docs.nginx.com/nginx/admin-guide/installing-nginx/installing-nginx-open-source/)
- A third-party lab writeup (not a scanner vendor) compared a version-only nginx check on one Ubuntu 26.04 host with the package changelog and Ubuntu’s CVE tracker. The author reports that all 16 advisories from the version-only check were already recorded as patched or not affected in the distro package, and calls that a 100% false-positive rate for that host. The same post says a version-only check correctly omitted one advisory whose upstream range, as the author lists it, was 1.30.0–1.30.5 and 1.31.2–1.31.6 and did not include the installed 1.28.3, while the distro changelog still mentioned the CVE. Those ranges are the blog’s claim; they were not re-checked against NVD for these notes. The post also says `server_tokens off` only stops banner scanners from flagging the version and does not fix the package. — [damonsec, 31 October 2026](https://www.damonsec.com/blog/check-nginx-version-vulnerable-backports)
- A banner-oriented scanner description lists `Server: Apache/2.4.29 (Ubuntu) OpenSSL/1.1.1f` as disclosing the web server, the TLS library, and the operating system, each with a version, and distinguishes an “exact” banner (`Server: nginx/1.25.3`) from a “distro build” whose number “may hide backported fixes.” It says none of those signals is a vulnerability by itself. — [WatchFor, 22 October 2026](https://watchfor.io/blog/what-your-server-headers-reveal)

### Inferences

- The backport false positive is the one pattern the scanner vendors document in their own words, for OS packages and for NVD CPE ranges. A `Server` header that shows an upstream version (`nginx/1.28.x`, `Apache/2.4.x`, `OpenSSL/1.1.1f`) is exactly the identifier those vendors refuse to match against upstream ranges when a distro package is what is actually installed. The header does not carry the Debian revision or the RPM epoch-release that Grype and Trivy compare.
- nginx stable versus mainline is a branch rule, not a single semver line. An even middle number is stable and receives backported security fixes without moving to the next odd mainline. Comparing a stable banner to a mainline “fixed in” version, or the reverse, is the wrong ordering. No Grype, Trivy, osv-scanner, or Dependency-Check page was found that states this nginx rule; it comes from nginx.
- A header that appends a module version (`OpenSSL/1.1.1f` on an Apache `Server` line, or `X-Powered-By` naming PHP while `Server` names nginx or Apache) is a different product identity. Matching the module’s version as if it were the server, or the server’s version as if it were the module, is the same class of mistake as Dependency-Check attaching a server CPE to a driver, or Grype attaching every source-package CVE to a binary built from that source. The WatchFor page documents the combined banner; the scanner vendors document the identity mistake, not the header.

### Gaps

- No official Grype, Trivy, osv-scanner, or Dependency-Check page was found that discusses HTTP `Server` banners, nginx stable versus mainline, or a header that names a module. The banner-specific pattern is assembled from nginx’s branch rules, OpenSSL’s vendor-support warning, and two non-vendor blog posts.
- The damonsec 16-of-16 figure is one host and one author’s reading of Ubuntu’s tracker. It is not a published false-positive rate for any of the four tools.
- Apache’s `ServerTokens` directive, which controls whether the `Server` header includes module versions, was not fetched. The combined Apache-plus-OpenSSL example is from the WatchFor article only.

## Can nginx or Apache be matched from a Server header without a lockfile?

### Takeaway

No. The four projects do not document a match from an HTTP `Server` header. They document packages, lockfiles, images, SBOMs, file evidence, and, for Grype only, a PURL or CPE the operator already constructed. Where they discuss a version that is not a single installed version, they say that is not sufficient for a precise finding.

### Cited Findings

- osv-scanner: “To scan the dependency versions selected for an environment, prefer a resolved lockfile.” If no lockfile exists, use a fully pinned manifest generated from the environment, such as `pip freeze`. “Manifest files can declare version ranges and do not necessarily record the versions installed in an environment. OSV-Scanner extracts versions from manifests on a best-effort basis. The exact behavior varies by ecosystem and extractor, so a version reported from a manifest may not be the version that is installed.” Supported inputs listed are lockfiles, manifests, container images, and SBOMs, not HTTP responses. — [Supported artifacts and manifests](https://google.github.io/osv-scanner/supported-languages-and-lockfiles/); [Usage](https://google.github.io/osv-scanner/usage/)
- Trivy: “When a package version cannot be uniquely determined (e.g., `package-a: ">=3.0"`), Trivy typically skips vulnerability detection for that package to avoid false positives. If a lock file is present with fixed versions, Trivy will use those for detection.” Non-packaged software is detected only from a Rekor SBOM, embedded Go or Rust module info, or an SBOM embedded in the image. OS packages are detected from the image, VM, or host package database. — [Trivy vulnerability scanning](https://github.com/aquasecurity/trivy/blob/main/docs/guide/scanner/vulnerability.md)
- Grype’s documented targets are an image, directory, file, SBOM, Zarf archive, PURL, or CPE. A CPE scan is described for “legacy systems that use CPE identifiers” or for testing “a specific CVE that references a CPE,” not for parsing a banner. The version field inside a CPE the operator passes, such as `cpe:2.3:a:apache:log4j:2.14.1:*:*:*:*:*:*:*`, is part of that supplied identifier. Nothing on the scan-target page reads a `Server` header. — [Supported scan targets](https://oss.anchore.com/docs/guides/vulnerability/scan-targets)
- Dependency-Check’s identification input is evidence taken from the files it scans (manifest, pom, package names), not a network banner. The project says the evidence method can be unreliable and that false positives and false negatives may exist. — [Internals](https://dependency-check.github.io/DependencyCheck/general/internals.html)
- nginx says a package shipped by a Linux distribution may not be the upstream tarball: maintainers control contents and update frequency, the package may be outdated, and many long-term-support distributions ship only the stable branch. The `Server` header version is not mentioned. — [Installing NGINX Open Source](https://docs.nginx.com/nginx/admin-guide/installing-nginx/installing-nginx-open-source/)
- OpenSSL, on the 1.1.1 EOL that still applies to anyone matching an `OpenSSL/1.1.1` token: “If your copy of OpenSSL 1.1.1 is from an Operating System vendor (e.g. via `.rpm` or `.deb` packages) or another third party then the support periods for them may differ to those provided by the OpenSSL Project itself. Check with the OS vendor/other third party on what support for OpenSSL they provide.” — [OpenSSL 1.1.1 End of Life](https://www.openssl.org/blog/blog/2023/09/11/eol-111)

### Inferences

- The limitation to quote for a header-based web scanner is Trivy’s and osv-scanner’s, even though both are talking about manifests rather than HTTP. A `Server` token such as `nginx/1.28.0` or `Apache/2.4.41 (Ubuntu)` is less specific than the lockfile or distro package those tools require: it has no Debian revision, no RPM epoch-release, and no proof of which branch or vendor build produced the number. Feeding that string through as if it were a resolved package version is the case Trivy says it skips when the version is not unique, and the case osv-scanner says may not be the installed version.
- Grype will compare a version if the caller first turns the banner into a PURL or a CPE. That is a documented interface, but the docs do not say the resulting match is valid for a distro-built nginx or Apache. Given the backport and CPE false-positive notes above, a CPE built only from the banner is the match path Grype disables by default for dpkg and treats as high false-positive risk.
- There is no documented nginx or Apache matcher that starts from a `Server` header and ends at a vendor advisory without a lockfile, an OS package database, or an SBOM.

### Gaps

- The sentence “a banner version is not sufficient” does not appear in the Grype, Trivy, osv-scanner, or Dependency-Check pages that were read. The quotations above are the closest written limitations, and they are about unpinned manifests, non-unique versions, and distro packages, not about the `Server` header by name.
- No primary Apache HTTP Server documentation page was fetched for `ServerTokens` or for how the `Server` header version relates to CVE ranges. The nginx limitation is from nginx’s install guide, which never mentions vulnerability scanners.
