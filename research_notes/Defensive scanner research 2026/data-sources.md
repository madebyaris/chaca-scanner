# Vulnerability data sources for an offline defensive version matcher (12 November 2026)

Scope: where published affected-version data comes from, how ranges are encoded, and what a small offline scanner can vendor. Advisory id plus an upgrade target only. No exploit detail is included below.

## What are the current primary sources, and for each who publishes it, how often it updates, what license applies, whether bulk download or an API exists, and whether ranges are machine-readable?

### Takeaway

For lockfile ecosystems the practical pair is OSV’s per-ecosystem zip (which already ingests the GitHub Advisory Database) plus the GitHub git mirror. For nginx, OpenSSL, Apache httpd, PHP, and WordPress core, the vendor page is still the place that states a version bound in the product’s own version numbers; NVD CPE and CVE JSON 5 sometimes carry that bound and sometimes carry only a sentence. There is no single license that covers an OSV `all.zip`.

### Cited Findings

#### OSV.dev

- OSV.dev aggregates records already encoded in the OpenSSF OSV format, plus conversions the OSV.dev team maintains for Debian security advisories, Alpine SecDB, and “NVD CVEs for open source software.” The schema is maintained by the OpenSSF Vulnerability Disclosures Working Group. Schema version on the spec page is 1.9.2, dated 13 October 2026. — [OSV data sources](https://google.github.io/osv.dev/data/); [OSV schema 1.9.2](https://ossf.github.io/osv-schema/)
- Named upstreams and the licenses OSV lists for them include GitHub Advisory Database (CC-BY 4.0), PyPI Advisory Database (CC-BY 4.0), Go Vulnerability Database (CC-BY 4.0), Rust Advisory Database (CC0 1.0), OSS-Fuzz (CC-BY 4.0), Ubuntu (CC-BY-SA 4.0), Alpine SecDB (CC-BY-SA 4.0), and Chainguard/Wolfi (CC-BY-NC-ND 4.0, plus a separate Chainguard license for commercial scanners). The data page does not state one license for the aggregated bucket. — [OSV data sources](https://google.github.io/osv.dev/data/)
- Bulk download: a GCS bucket `gs://osv-vulnerabilities`, also over HTTPS at `https://storage.googleapis.com/osv-vulnerabilities/`. Full database: `all.zip` (includes withdrawn records). Per ecosystem: `<ECOSYSTEM>/all.zip` and `<ECOSYSTEM>/<ID>.json`. #### NVD (NIST)

- NIST publishes the National Vulnerability Database. On 15 April 2026 NIST said it will still list every submitted CVE, but will enrich (severity and product lists) on a priority list: CISA KEV (goal: within one business day of receipt), software used in the federal government, and critical software as defined under EO 14028. Everything else is “Lowest Priority - not scheduled for immediate enrichment.” Users can ask for enrichment by emailing nvd@nist.gov. NIST also said it will no longer routinely add its own severity score when the CNA already provided one, and it will re-analyze a modified enriched CVE only when it knows the modification materially affects the enrichment. Backlog CVEs with an NVD publish date earlier than 1 March 2026 move to “Not Scheduled,” except KEV entries, which were already prioritized. — [NIST, 15 April 2026, updated 17 April 2026](https://www.nist.gov/news-events/news/2026/04/nist-updates-nvd-operations-address-record-cve-growth)
- Same announcement: CVE submissions increased 263% between 2020 and 2025; NIST enriched nearly 42,000 CVEs in 2025; submissions in the first three months of 2026 were nearly one-third higher than the same period in 2025. — [NIST, 15 April 2026](https://www.nist.gov/news-events/news/2026/04/nist-updates-nvd-operations-address-record-cve-growth)
- The live CVE API used here is `GET https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=CVE-2021-23017`, which returned HTTP 200 and `application/json` on 12 November 2026. The record includes both `configurations` (CPE match objects with version bounds) and `affected` (CNA affected-product data). — that URL, 12 November 2026
- NIST’s start-here page states the public rate limit without an API key is 5 requests in a rolling 30-second window, and 50 requests in a rolling 30-second window with an API key, passed in a request header. It recommends sleeping for several seconds between requests. — [NVD start here](https://nvd.nist.gov/developers/start-here)
- The terms-of-use page says use may be limited, keys must not be shared, limits for users behind one proxy apply to that proxy, the API is “as is” and “as-available,” and the numeric public rate limit is the one posted at `nvd.nist.gov/developers` rather than restated in the terms. The search index dated that terms page 23 September 2026. The terms excerpt retrieved does not name an SPDX license or say “public domain.” — [NVD API terms of use](https://nvd.nist.gov/developers/terms-of-use)
- Older NIST pages, not 2025–2026 policy: a 2022 announcement said the CVE and CPE APIs are the preferred way to stay up to date and that data feeds would be retired about 12 months after the 2.0 APIs. An archived 17 October 2024 copy of the NVD change timeline still said legacy data-feed files would be retired in 2024 once bulk-download improvements existed, and that 1.0 APIs would be retired 18 December 2023. ### Inferences

- A scanner that vendors `all.zip` is vendoring many licenses at once, including share-alike (Ubuntu, Alpine) and a non-commercial Chainguard term. Per-ecosystem zips for npm, Go, and crates.io avoid that mix if those ecosystems’ own upstream licenses (CC-BY 4.0 or CC0, as listed) are the ones that matter.
- NIST’s current instruction for NVD is “call the API,” which is a poor fit for a fully offline tool. CVE.org is the source that tells a daily offline job to take the midnight zip.
- Vendor HTML is machine-readable only after a scraper. The strings are regular (nginx “Vulnerable” / “Not vulnerable”; OpenSSL “from A before B”; Apache “Affects X through Y”) but they are not a schema, and Apache sometimes omits the start bound.

### Gaps

- No 2026 NIST page was retrieved that says, in one sentence, whether the legacy JSON zip feeds are still served. The 2022 retirement plan, the October 2024 archive, and the FKIE claim disagree. Do not treat FKIE year files as NVD.
- NIST terms excerpted here do not state a license name. A third-party OpenAPI mirror calls NVD data public domain; that phrase was not on the NIST page retrieved.
- Numeric API details often repeated elsewhere (maximum 2000 CVEs per page, 120-day date windows) were not re-read from `nvd.nist.gov` in this pass. Only the 5/50-per-30-seconds figures were on the start-here snippet.
- GitHub’s git-mirror refresh interval is not stated. PHP’s per-CVE affected-version publication (changelog versus a feed) was not opened. No Apache JSON feed was found on the 2.4 HTML page; one could exist at another URL. CVE Program terms of use were not opened, only pointed to.
- `cvelistV5` `main.zip` returned no `Content-Length`. No source consulted states a byte size for the CVE List zip.

## How do OSV, NVD CVE JSON 5, and GitHub advisory records encode affected versions?

### Takeaway

OSV encodes ranges as ordered events (`introduced`, `fixed`, `last_affected`, `limit`) under a type of `SEMVER`, `ECOSYSTEM`, or `GIT`, optionally plus an explicit `versions` list. CVE JSON 5 encodes them as `versions[]` objects with `version`, `status`, and optionally `versionType` plus `lessThan` or `lessThanOrEqual`; many CNAs still put the whole range in one prose `version` string. NVD’s API 2.0 record is a third shape: CPE `cpeMatch` objects with `versionStartIncluding` / `versionStartExcluding` / `versionEndIncluding` / `versionEndExcluding`, and it may also echo the CNA prose. GitHub’s git files are OSV; GitHub’s REST API is a separate string field, `vulnerable_version_range`.

### Cited Findings

#### OSV (schema 1.9.2, 13 October 2026)

- Field path: `affected[].package.ecosystem`, `affected[].package.name`, `affected[].package.purl`, `affected[].ranges[].type`, `affected[].ranges[].events[]`, `affected[].ranges[].repo` (required when type is `GIT`), `affected[].versions[]`. — [OSV schema](https://ossf.github.io/osv-schema/)
- `type` is one of `SEMVER` (SemVer 2.0.0 ordering, no leading “v”; ranges must not overlap; an explicit `versions` list is not required), `ECOSYSTEM` (ecosystem-specific ordering; the spec recommends also listing `versions` because a generic client cannot evaluate the range), or `GIT` (full commit hashes; needs the repo graph; does not remove the need for an enumerated `versions` list). — [OSV schema](https://ossf.github.io/osv-schema/)
- Each event object has exactly one of `introduced`, `fixed`, `last_affected`, `limit`. At least one `introduced` is required. `introduced` may be `"0"` to mean “before any version.” If there is no `limit`, an implicit `{ "limit": "*" }` applies. `fixed` and `last_affected` are not both used; the spec says versions above `last_affected` are treated as unaffected and that this can false-negative, so `fixed` is preferred. A version is vulnerable if it is in `versions[]` or a range contains it: at or after `introduced`, before `fixed`, and not after `last_affected`, and before a `limit`. — [OSV schema](https://ossf.github.io/osv-schema/)
- Real record, version bounds only, from `POST https://api.osv.dev/v1/query` on 12 November 2026. Id `GHSA-vh95-rmgr-6w4m`, alias `CVE-2020-7598`, package `pkg:npm/minimist`. Two `SEMVER` ranges, no enumerated `versions`: events `introduced` `0` then `fixed` `0.2.1`; and `introduced` `1.0.0` then `fixed` `1.2.3`. — that API call

#### CVE JSON 5 (this is the CVE Program record, not the NVD CPE object)

- The schema docs say a range is a version object with `version`, `versionType`, `status`, and either `lessThan` or `lessThanOrEqual`. `versionType` is required for a range because order is not universal (`semver` is given as one type; the docs note Maven order differs). Meaning they state: `version` ≤ V ≤ `lessThanOrEqual`, or `version` ≤ V < `lessThan`. Their illustrative objects use 2.0.0 / 2.5.1 and 2.0.0 / 2.5.2; those are documentation examples, not a published advisory. — [CVE schema versions.md](https://raw.githubusercontent.com/CVEProject/cve-schema/main/schema/docs/versions.md)
- Real record that does use the fields. `CVE-2026-108142` in cvelistV5, `dataVersion` 5.2, `containers.cna.affected[]`: vendor `Veeam`, product `Backup and Replication`, `defaultStatus` `unaffected`, and `versions` entries `version` `13.0`, `status` `affected`, `lessThan` `13.0.3`, `versionType` `semver`; and `version` `13.1`, `lessThan` `13.1.2`, `versionType` `semver`. — [CVE-2026-108142.json](https://github.com/CVEProject/cvelistV5/blob/main/cves/2026/108xxx/CVE-2026-108142.json)
- Real record that does not use a bound field. CVE-2021-23017, `dataVersion` 5.1, fetched from `https://cveawg.mitre.org/api/cve/CVE-2021-23017` on 12 November 2026: one `versions` object whose only version-related keys are `status` `affected` and `version` set to the sentence “Nginx Web Server versions 0.6.18 thru 1.20.0 before 1.20.1, Nginx plus versions R13 thru R23 before R23 P1. Nginx plus version R24 before R24 P1”. There is no `lessThan`, `lessThanOrEqual`, or `versionType`. — that API response
- Kernel records use the same object for git hashes. The cvelist file for CVE-2025-40050 shows `versionType` `git` with `version` and `lessThan` set to commit hashes, and a separate affected block using `version` `6.17` with `status` `affected` and `defaultStatus` `affected`, plus `version` `0`, `lessThan` `6.17`, `status` `unaffected`, `versionType` `semver`. A fingerprinted kernel release string is not the same field as the git hash. — [CVE-2025-40050.json](https://github.com/CVEProject/cvelistV5/blob/main/cves/2025/40xxx/CVE-2025-40050.json)

#### NVD API 2.0 (what NIST actually serves for version matching)

- For CVE-2021-23017 the `configurations` tree contains `cpeMatch` objects. Fields present on the nginx match: `criteria` `cpe:2.3:a:f5:nginx:*:*:*:*:*:*:*:*`, `vulnerable` true, `versionStartIncluding` `0.6.18`, `versionEndExcluding` `1.20.1`. The same CVE’s configuration list also has matches for OpenResty (`versionEndExcluding` `1.19.3.2`), Fedora versions 33 and 34 with no version range, and several Oracle and NetApp products. — `https://services.nvd.nist.gov/rest/json/cves/2.0?cveId=CVE-2021-23017`, 12 November 2026
- The same NVD record’s `affected` array is not the CPE object. It is `affected[].source` plus `affected[].affectedData[]` with `vendor`, `product`, and `versions[].version` / `versions[].status`. For this CVE, `version` is the same prose sentence as the CVE JSON 5.1 record, and there is no `lessThan`. — same NVD response
- So “NVD CVE JSON 5” is two encodings in one payload: CPE match bounds when NIST has enriched the CVE, and a copy of the CNA `affected` data which may be unstructured. The nginx.org lines for this CVE (“Vulnerable: 0.6.18-1.20.0”, “Not vulnerable: 1.21.0+, 1.20.1+”) are a third wording. This note does not claim those three are equivalent. — [nginx advisories](https://nginx.org/en/security_advisories.html); NVD and CVE AWG responses above

#### GitHub

- Files in `github/advisory-database` are OSV, so they use `affected[].ranges[].events` as above. GitHub also documents a non-OSV field `database_specific` on a range, `last_known_affected_version_range`, for range text that OSV events cannot represent or that GitHub tracks separately. The README says consumers should not rely on `database_specific` unless told to, and that it can appear in addition to or instead of OSV events. — [README](https://github.com/github/advisory-database/blob/main/README.md)
- The REST resource is different. On 12 November 2026, `GET https://api.github.com/advisories` returned `GHSA-q6jf-24jf-m3cg` (CVE-2026-120792). One of its `vulnerabilities[]` entries, package ecosystem `npm`, name `@microsoft/aspire-cli`, has `vulnerable_version_range` `>= 13.4.2, < 13.6.5` and `first_patched_version` `13.6.5`. Those are strings, not `introduced`/`fixed` events. The same advisory also has NuGet packages with their own ranges (for example `Aspire.Cli`, `>= 13.2.0, < 13.6.5`, first patched `13.6.5`). — that API response

### Inferences

- An offline matcher needs three comparators, not one: OSV event evaluation (and, for `ECOSYSTEM`, ideally the enumerated `versions` list), CPE interval fields, and a fallback when the only “version” is a sentence. The nginx CVE is the worked example of the fallback: the CNA record has no `lessThan`, while nginx.org and the NVD CPE object do state bounds.
- GitHub REST `vulnerable_version_range` is convenient for an upgrade string (`first_patched_version`) but it is not the OSV object. Matching code that reads the git mirror must not assume the REST string is present in the file, and the reverse.

### Gaps

- The OSV schema’s own examples (`fixed` `1.0.2`, `last_affected` `2.1.214`) are spec examples. They were not used as real advisories.
- No NVD record was pulled that shows `versionStartExcluding` or `versionEndIncluding` populated. The field names are present in the schema of the object that was returned; only the nginx match’s populated keys are cited.
- Whether GitHub’s OSV file for `GHSA-q6jf-24jf-m3cg` repeats the REST string inside `last_known_affected_version_range` was not checked.

## Which sources fit web-server and library fingerprints, and which fit dependency lockfiles?

### Takeaway

npm, crates.io/cargo, and Go lockfiles should be matched against OSV ecosystem zips or the GitHub reviewed advisory set, which name the registry package and a range. nginx, OpenSSL, Apache httpd, PHP, and WordPress core should be matched against the vendor page, with NVD CPE used only where an enriched `cpeMatch` exists for that product. OSV’s ecosystem list, as of 12 November 2026, has no ecosystem for those five products. Distro OSV ecosystems (Debian, Ubuntu, Alpine) name distro packages, which are not the same string as an upstream version fingerprint.

### Cited Findings

- OSV `ecosystems.txt` includes `npm`, `Go`, `crates.io`, `Packagist`, `Maven`, and `PyPI`, and also `Debian`, `Ubuntu`, `Alpine`, and `GIT`. It has no nginx, OpenSSL, httpd, PHP, or WordPress ecosystem name. — [ecosystems.txt](https://storage.googleapis.com/osv-vulnerabilities/ecosystems.txt), 12 November 2026
- GitHub reviews advisories only when they map to a supported registry. The documented list is Composer, Hex, Go, GitHub Actions, Maven, npm, NuGet, PyPI, Pub, RubyGems, crates.io, and Swift. Unreviewed rows are NVD imports that are not package-mapped, and Dependabot does not alert on them. — [About the GitHub Advisory Database](https://docs.github.com/en/code-security/security-advisories/working-with-global-security-advisories-from-the-github-advisory-database/about-the-github-advisory-database)
- The minimist OSV record and the Aspire npm REST record show lockfile-shaped data: ecosystem name, package name, purl or registry name, and a range whose fixed end is a version you can print as an upgrade. — OSV query and GitHub API, 12 November 2026
- nginx.org, the OpenSSL vulnerability index, and the Apache 2.4 page each state upstream version bounds in the version scheme a banner scan would see (see the CVE-2021-23017, CVE-2026-88823, and CVE-2026-119618 bounds in the first section). — [nginx](https://nginx.org/en/security_advisories.html); [OpenSSL](https://openssl-library.org/news/vulnerabilities/); [Apache httpd 2.4](https://httpd.apache.org/security/vulnerabilities_24.html)
- NVD CPE can carry a product interval when the CVE was enriched. CVE-2021-23017’s nginx CPE has `versionStartIncluding` `0.6.18` and `versionEndExcluding` `1.20.1`, but the same configuration set names other products. NIST’s April 2026 policy says product-list enrichment is no longer applied to every CVE. — NVD API response; [NIST, 15 April 2026](https://www.nist.gov/news-events/news/2026/04/nist-updates-nvd-operations-address-record-cve-growth)
- PHP’s official machine-readable-looking page is a support window (two years full support, two years critical security only), not a CVE-to-version map. WordPress’s official statement of “what to upgrade to” is the release post for that branch. — [PHP supported versions](https://www.php.net/supported-versions.php); [WordPress 7.0.2](https://wordpress.org/news/2026/07/wordpress-7-0-2-release/)
- Packagist is an OSV ecosystem and a GitHub ecosystem. That covers PHP libraries in Composer lockfiles, not the PHP interpreter version a server banner shows. — [OSV data sources](https://google.github.io/osv.dev/data/); [GitHub docs](https://docs.github.com/en/code-security/security-advisories/working-with-global-security-advisories-from-the-github-advisory-database/about-the-github-advisory-database)

### Inferences

- For a banner-scanning product the authoritative upgrade string for those five products is the vendor line (“Not vulnerable: 1.31.7+, 1.30.6+”, “before 4.1.1”, “fixed in 2.4.71”, “6.9.5”). NVD is a secondary index that is incomplete by NIST’s own 2026 policy and that mixes vendors inside one CVE.
- For a lockfile scan, querying NVD by CPE is the wrong key. The package name and ecosystem already exist on the OSV and GitHub records.
- Debian/Ubuntu/Alpine OSV data would answer “is this distro package affected,” which is a third identifier (distro version plus package version), not a substitute for either upstream fingerprint or a language lockfile.

### Gaps

- No OSV query was run for the package name `nginx` or `openssl` under the `GIT` ecosystem, so it is not shown whether some git-commit records exist outside `ecosystems.txt` names. The ecosystem list itself has no product ecosystem for them.
- WordPress plugin and theme advisories (as opposed to core release posts) were not surveyed. PHP release-note pages that might name a fixed interpreter version per CVE were not opened.

## What data-quality problems are documented, including missing ranges, disputed or changing versions, kernel versus product CPE, and lag?

### Takeaway

The quality failures that change a version match are: CNA “affected” text with no `lessThan`, NVD product enrichment that is now officially skipped for most CVEs, kernel records whose bounds are git commits and per-branch stable versions rather than one linear version, and ranges that the CNA later tightens or revokes. Severity lag is real but it is not what a version matcher reads.

### Cited Findings

- Missing structured range, primary records: CVE-2021-23017’s CVE JSON 5.1 `versions[].version` is one English sentence and has no `lessThan`. NVD copies that sentence into `affectedData` and, separately, stores a CPE interval. nginx.org states yet another pair of strings for the same CVE. — CVE AWG, NVD API, and [nginx.org](https://nginx.org/en/security_advisories.html), as cited above
- A 6 November 2026 analysis of CVE records (author’s counts, not a CVE Program statistic) says that among records published in 2026 through 7 September, GitHub CNA records had an affected version range on 100% (n=9,599) and MITRE, as CNA of last resort, had one on 14% (n=2,918). The same piece says 2025 MITRE records had a range on 13% (n=5,203). — [Cloud Security Partners, 6 November 2026](https://www.cloudsecuritypartners.com/blog/nobody-waits-for-your-project-to-be-ready-for-its-first-cve)
- NIST, 15 April 2026: enrichment, which is what adds the product list a CPE matcher needs, is not scheduled for CVEs outside KEV, federal software, and EO 14028 critical software. The pre-1 March 2026 backlog of unenriched CVEs was moved to “Not Scheduled.” NIST also stopped routinely publishing a second severity score. Volume context in that post: +263% submissions from 2020 to 2025, about 42,000 enriched in 2025, Q1 2026 submissions about one-third above Q1 2025. — [NIST](https://www.nist.gov/news-events/news/2026/04/nist-updates-nvd-operations-address-record-cve-growth)
- CSO Online, 4 June 2026, reporting the Commerce Department inspector general: NIST had no sustainable process for NVD submissions and had not cleared the backlog. The article says NIST and CISA both enrich, and that NIST would not ingest CISA’s enrichment until the NVD could attribute the source, which the article says was only possible after March 2025. The OIG PDF itself was not opened here; a news-site copy titled OIG-26-020-I was indexed with the sentence that the backlog grew from about 13,000 at the start of June 2024 to over 27,000 by the end of 2025, and that assigning a CPE applicability statement is most of the enrichment work. Treat the PDF mirror as unverified against `oig.doc.gov`. — [CSO Online](https://www.csoonline.com/article/4181438/us-government-report-slams-nist-for-nvd-backlog.html); [mirrored PDF text in search](https://www.heise.de/downloads/18/5/0/9/2/8/1/7/OIG-26-020-I-SECURED.pdf)
- Expert Insights, 21 November 2025, summarizing Sonatype: in 2025, 62% of open-source CVEs had overstated severity scores, 64% had no NVD severity score, the average time from public disclosure to an NVD score was 6 weeks, and “inconsistent or too broad advisory metadata” produced version-range errors and false alerts. The Sonatype report PDF was not opened. — [Expert Insights](https://expertinsights.com/news/research-reveals-major-flaws-in-cve-program)
- Vendor-name CPE collisions, academic: arXiv 2505.13895 (20 May 2025) says 50.18% of vendor names in NVD CPEs were inconsistent, and 47.07% of vendor names drawn from CVEDetails were inconsistent. — [arXiv:2505.13895](https://arxiv.org/html/2505.13895v1)
- One CVE, many products: the enriched NVD record for the nginx CVE-2021-23017 includes CPE matches for F5 nginx, OpenResty, Fedora, NetApp, and Oracle products. A matcher that keys only on the CVE id, or on a loose product token, will cross vendors. — NVD API, 12 November 2026
- Kernel versus a product version string. Greg Kroah-Hartman, 31 January 2025: kernel.org is the CNA; entries carry git commit ids for the vulnerable ranges; entries are updated over time, including revocations and tighter ranges; consumers that read a CVE once and never refresh are wrong; raw data is `https://git.kernel.org/pub/scm/linux/security/vulns.git/` if you do not want the cve.org JSON. The kernel CVE process doc he points at is `https://www.kernel.org/doc/html/latest/process/cve.html`. — [social.kernel.org notice](https://social.kernel.org/notice/AqeMuSrRtRMdXOSRQ8)
- Bootlin, 10 November 2026: kernel.org describes vulnerabilities against mainline and stable branches, and a naive numeric compare of kernel versions produces both false positives and false negatives. Their checker now tests the version against the branch the range describes, and treats `6.12` and `6.12.34` as different kinds of versions. — [Bootlin](https://bootlin.com/blog/sbom-cve-check-1-4-0-released/)
- The CVE-2025-40050 cvelist record shows the encoding underneath that warning: `versionType` `git` with commit-hash `version` and `lessThan`, alongside a `6.17` / `semver` block. — [CVE-2025-40050.json](https://github.com/CVEProject/cvelistV5/blob/main/cves/2025/40xxx/CVE-2025-40050.json)
- OSV’s schema itself warns that `last_affected` marks a ceiling at publication time and can false-negative later, and that `ECOSYSTEM` ranges may be unevaluable without the ecosystem’s version list. OSV.dev says it fills `affected.versions[]` during import when it can. — [OSV schema](https://ossf.github.io/osv-schema/); [OSV FAQ](https://google.github.io/osv.dev/faq/)
- Apache’s 2.4 page states two quality flags in the format itself: a question mark means the affected version was not verified, and a “-dev” fix version is not a release. At least one 2026 entry gives no start bound (“Affects through 2.4.68”). — [httpd vulnerabilities_24](https://httpd.apache.org/security/vulnerabilities_24.html)

### Inferences

- For this scanner, “lag” means a missing product interval, not a missing CVSS score. After 15 April 2026 a new CVE can be in NVD and still have no CPE to match a banner against. The vendor page can have the bound earlier or later; neither side is a complete clock.
- Kernel CVEs should not be matched by sorting version strings against `lessThan`. That is a different product from nginx/OpenSSL/httpd version compare, even though both use CVE ids.
- “Disputed version” in the sense of a formal dispute flag was not observed. What was observed is weaker and more useful: ranges that are prose, ranges that are later tightened, and ranges that are revoked. A snapshot that never refreshes will keep the old bound.

### Gaps

- The OIG report was not read from an `oig.doc.gov` URL. The backlog figures 13,000 and 27,000 are from a mirrored PDF excerpt, not from NIST’s April note.
- Sonatype’s 19,945 false positives and 156,474 false negatives, mentioned in the same Expert Insights article, are not repeated here as findings because the underlying report was not opened and the excerpt does not define the denominator.
- No count was made of how many nginx, OpenSSL, or httpd CVEs in 2026 have CPE bounds versus prose only.

## What do maintainers recommend for an offline tool: a shipped snapshot, a scheduled refresh, or a live query? What are the snapshot file names, and how big are they if a source says?

### Takeaway

OSV documents a snapshot plus an incremental CSV, not a live query, as the way to download the database. CVE.org tells a daily job to take the midnight baseline zip and an hourly job to take delta zips. NIST tells automation to use the rate-limited API and has not, in the pages read here, published a supported full-database zip for 2026. GitHub’s offline artifact is the git repository of OSV files. Vendor pages have no snapshot format.

### Cited Findings

- OSV: download `gs://osv-vulnerabilities/all.zip` or `https://storage.googleapis.com/osv-vulnerabilities/<ECOSYSTEM>/all.zip`. To avoid re-downloading everything, stream `modified_id.csv` (root file covers all ecosystems; each ecosystem directory has its own) and stop when the timestamp is already applied. The export job is continuous. Individual records are `<ECOSYSTEM>/<ID>.json`. — [OSV data sources](https://google.github.io/osv.dev/data/)
- Observed sizes on 12 November 2026, HTTP `Content-Length`, not a documented estimate: full `all.zip` 2,940,295,302 bytes; `npm/all.zip` 220,559,266 bytes. — `https://storage.googleapis.com/osv-vulnerabilities/all.zip` and `https://storage.googleapis.com/osv-vulnerabilities/npm/all.zip`
- The live OSV API exists in addition to the dumps (`POST /v1/query` returned a record). The data page presents the bucket, not the API, as the download. — [OSV data sources](https://google.github.io/osv.dev/data/); query call 12 November 2026
- CVE Program downloads page, 10 November 2026: if you update daily or less often, use the midnight baseline zip `Year-Month-Day_all_CVEs_at_midnight.zip` (unchanged for 24 hours). If you need hourly accuracy, use `Year-Month-Day_delta_CVEs_at_HH00Z.zip`, which contains only the deltas since the baseline. Git clone of `CVEProject/cvelistV5` is also a supported copy; the README says it tracks the CVE Services API about every 7 minutes. The page says the zips are large and does not state bytes. Legacy bulk formats ended 30 June 2024. — [cve.org/downloads](https://www.cve.org/downloads); [cvelistV5 README](https://github.com/CVEProject/cvelistV5)
- NVD: the 2022 NIST announcement, still the linked policy, says the CVE and CPE 2.0 APIs are the preferred update mechanism and describes feeds as something to retire. The start-here page tells clients to stay inside 5 requests per 30 seconds without a key, or 50 with a key, and to sleep between calls. A full historical pull through that limit is a multi-day job; NIST does not, on these pages, say “ship this zip.” — [NIST on feeds and APIs](https://nvd.nist.gov/General/News/changes-to-feeds-and-apis); [start here](https://nvd.nist.gov/developers/start-here)
- Whether NIST still serves legacy JSON feeds in November 2026 is unresolved. See the conflict in the first section. The FKIE repo is an unofficial API mirror that publishes its own daily `CVE-<year>.json.xz` release assets; its README says it is not endorsed by NVD. — [fkie-cad/nvd-json-data-feeds](https://github.com/fkie-cad/nvd-json-data-feeds)
- GitHub: clone `github/advisory-database` (OSV JSON, CC-BY 4.0) for an offline copy, or call `GET /advisories` for a live query. The README warns the layout can change incompatibly. EPSS on the database is refreshed daily, so a clone goes stale on that field even if the range does not. — [README](https://github.com/github/advisory-database/blob/main/README.md); [about page](https://docs.github.com/en/code-security/security-advisories/working-with-global-security-advisories-from-the-github-advisory-database/about-the-github-advisory-database)
- Kernel.org’s 2025 guidance is the opposite of a one-time snapshot: pull repeatedly, because ranges are tightened and CVEs are revoked, and prefer `vulns.git` if the cve.org JSON is the wrong shape. — [Greg Kroah-Hartman, 31 January 2025](https://social.kernel.org/notice/AqeMuSrRtRMdXOSRQ8)
- nginx, OpenSSL, Apache httpd, PHP, and WordPress do not publish an equivalent zip. Their offline artifact would be a scrape or a hand-maintained extract of the HTML or plaintext advisory. OpenSSL’s plaintext files are one file per disclosure date (`/news/secadv/20261110.txt`), not a database. — vendor URLs in the first section

### Inferences

- For lockfiles, the maintainer-shaped design is: ship the OSV ecosystem zips you actually match (npm, crates.io, Go; Packagist if PHP libraries matter), refresh on a schedule with `modified_id.csv`, and do not call the API on the scan path. GitHub’s git repo is redundant if those OSV zips already contain the GHSA records, which the OSV data page says they do, but the GitHub repo is the better source if you need `database_specific` or a review flag OSV might not treat as matching input.
- For NVD CPE, the honest offline design is a local cache filled by the API on a schedule, within the key’s rate limit, knowing the cache will lack product bounds for CVEs NIST has marked lowest priority. It is not a file NIST currently tells you to vendor.
- For CVE JSON 5 prose and `lessThan` bounds, the midnight cvelist zip is the artifact the program tells a daily tool to keep. It still will not contain a machine-readable nginx range when the CNA wrote a sentence.
- Vendor bounds for the five fingerprinted products have to be snapshotted by the product itself. Nothing in OSV or NVD replaces that snapshot under current coverage and enrichment policy.

### Gaps

- No OSV page states a recommended refresh interval in hours, only that the bucket is continuous and that `modified_id.csv` is how to take the delta.
- No byte size for the CVE List baseline zip was stated by cve.org or returned as `Content-Length` for `main.zip`.
- NIST bulk-download “improvements” mentioned in the October 2024 timeline were not found as a 2026 download URL.
